# Модуль Fleet (автопарк): цель и состав функций

Документ фиксирует **целевой охват** продукта. Реализация по пунктам ведётся постепенно; статус в коде может отставать от этого списка.

**Лицензирование / продажа отдельно:** доступ к API и продуктовому контуру Fleet для тенанта управляется флагом `tenant.settings.modules.fleet` (по умолчанию включён; выключение даёт HTTP 403 на `/api/v1/fleet/*` при сохранении ролевых прав). Платформа может выставлять модуль в админке тенанта вместе с матрицей ролей. Целевая модель — **дополнительно** включение Fleet на уровне **company** и scope прав по company+module; см. [`ADR-003`](../specs/architecture/ADR-003-tenant-company-module-data-boundaries.md). Пять независимых продуктовых модулей и биллинг: [`ADR-004`](../specs/architecture/ADR-004-five-product-modules-and-billing-events.md). **Настройки модуля Fleet** (шаблоны ТС, чек-листы, правила назначений) — на уровне **Company Module Settings**, см. [`ADR-005`](../specs/architecture/ADR-005-three-level-settings-hierarchy.md). Сводная **карта ключей и маршрутов**: [`module-catalog-and-routing-map.md`](../specs/architecture/module-catalog-and-routing-map.md).

## Цель

Дать тенанту сквозной контур управления автопарком: ресурсы (ТС, прицепы, водители), планирование и исполнение (календарь, назначения, ротация), контроль (телематика, тахограф, нарушения, сверка данных), экономика и отчётность (калькулятор расчётных сценариев, зарплата, отчёты), связь с HR и контрагентами, а также дашборд и настройки модуля. Доступ и лицензирование — отдельная зона (роль fleet, квоты мест), не смешиваемая с рекрутерским пулом без явного продуктового решения.

Публичные формы (чек-листы передачи, damage report, осмотры и т.д.) при необходимости строятся на платформенном модуле **Forms** — см. [`ADR-007`](../specs/architecture/ADR-007-forms-platform-capability.md), [`../forms/module-scope.md`](../forms/module-scope.md). Документы водителей и ТС (права, Code 95, тахограф, протоколы, GITD/IMI и т.д.) — **Document Hub** ([`ADR-009`](../specs/architecture/ADR-009-document-hub-platform-layer.md), [`../document-hub/module-scope.md`](../document-hub/module-scope.md)).

## Настройки модуля (ADR-005)

Каноническое хранение конфигурации Fleet **внутри компании** — таблица `company_module_settings`, строка с `module_key=fleet`. Эффективный доступ к модулю: тенант **`fleet` включён** и пересечение с `Company.enabled_modules` (`company_allows_module`, см. `backend/app/services/company_module_access.py`).

| Уровень | Что задаёт для Fleet |
|--------|------------------------|
| **Tenant** | Модуль `fleet` на workspace, матрица ролей, security; без операционных шаблонов конкретного клиента |
| **Company** | `enabled_modules`, привязки пользователей, visibility, карточка компании |
| **Module Settings (per company)** | Коды типов ТС, шаблоны документов на ТС, шаблоны чек-листов передачи, правила назначений, настройки damage report, шаблоны осмотров — в `settings_json` |

Типизированная схема **`FleetModuleSettingsV1`** в `backend/app/schemas/company_module_settings_json.py`: `version: 1`, опционально `vehicle_type_codes`, `vehicle_document_template_ids`, `handover_checklist_template_ids`, `assignment_rules`, `damage_report_settings`, `inspection_template_ids`. На **`PATCH`** — строгая валидация (`extra=forbid`); на **`GET`** битый legacy-JSON приводится к умолчаниям схемы.

**API:** `GET` / `PATCH /api/v1/companies/{company_id}/module-settings/fleet`; список строк по компании — `GET .../module-settings` (строки отфильтрованы по `company_allows_module`). **Роли API:** чтение — `administrator`, `supervisor`, `hr_officer`; запись — `administrator`, `supervisor` (`backend/app/api/v1/company_module_settings.py`). Роль **`fleet_manager`** в этом API пока **не** участвует; при продуктовом решении «настройки парка видит только fleet» — расширять зависимости роутера и матрицу согласованно.

**UI (MVP):** в SPA на карточке компании — блок настроек модулей с вкладкой Fleet: JSON и флаг «включено для модуля»; на фронте просмотр также для `workforce.view`, правка — `companies.manage` (сервер для fleet по-прежнему требует роли из списка выше).

## Функциональные блоки

| Блок | Назначение |
|------|------------|
| **Дашборд** | Сводка KPI: занятость ресурсов, нарушения, исполнение назначений, алерты телематики/тахографа. |
| **Автомобили** | Учёт ТС, статусы, привязки к парку/линиям, документы и операции жизненного цикла. |
| **Прицепы** | Учёт прицепного состава, сцепки с ТС, ограничения в назначениях. |
| **Водители** | Карточки водителей, допуски, участие в сменах, назначениях и ротации. |
| **Контрагенты** | Заказчики, перевозчики, подрядчики: договоры, реквизиты, участие в линиях и расчётах. |
| **Назначения** | Распределение рейсов/смен/задач на ТС и водителей, статусы выполнения. |
| **Линии обслуживания** | Регулярные маршруты/сервисы, привязка ресурсов и расписаний; сменность по месяцам выводится из фактических данных (история назначений и далее — из телематики/объёмов), а не задаётся отдельной «надстройкой» коэффициентов. |
| **Связка с HR** | Сотрудники, должности, отсутствия; соответствие водителя учётной записи и кадровым данным. |
| **Ротация** | Шаблоны циклов работа/отдых, применение к сменам и календарю. |
| **Календарь** | Единое представление смен, занятости ТС и водителей, событий и контрольных дат. |
| **Калькулятор** | Расчёты по правилам продукта: тарифы, пробег/часы, надбавки, предварительная зарплата или себестоимость рейса (уточняется в спецификации расчётов). |
| **Телематика** | Приём и отображение данных о движении/состоянии ТС; основа контроля и сверки. |
| **Тахограф** | Учёт режима труда и отдыха, лимиты и предупреждения по данным тахографа. |
| **Нарушения** | Регистрация и классификация нарушений (скорость, режим, документы и т.д.). |
| **Сверка данных** | Сопоставление телематики, тахографа, назначений и фактических событий; выявление расхождений. |
| **Зарплата** | Начисления по правилам (смены, рейсы, штрафы/премии), связь с калькулятором и отчётами. |
| **Отчёты** | Регламентированные и операционные выгрузки для внутреннего использования и контрагентов. |
| **Настройки** | Правила парка, интеграции, доступы, параметры календаря и расчётов. |

## Сопровождение

- При изменении охвата обновляйте этот файл и задачи в бэклоге (Linear/Jira и т.п.).
- Детали API и схемы БД — в коде (`backend/app`, маршруты и модели fleet) и в миграциях Alembic.
- Сводка для дашборда: `GET /api/v1/fleet/overview` — агрегаты по ТС/прицепам/водителям/линиям/моделям работы/назначениям; разбивки по статусам для **ТС** (`vehicles_by_status`), **прицепов** (`trailers_by_status`), **водителей** (`drivers_by_status`), **операционных линий** (`operating_lines_by_status`) и **назначений** (`assignments_by_status`); число водителей с привязкой к workforce: `drivers_with_workforce_total`; строки ростера на линиях (membership в `fleet_operating_line_vehicles` / `fleet_operating_line_drivers`): `line_roster_vehicles_total`, `line_roster_drivers_total` (один ресурс может иметь несколько строк на разных линиях); для водителей на линии с учётом интервалов `effective_from` / `effective_to`: `line_roster_drivers_effective_today_total` (календарный **день UTC** на сервере); пересечение интервалов назначения (`service_start` … `coalesce(service_end, service_start)`) с **сегодня (UTC)** и с **текущим календарным месяцем (UTC)**: `assignments_overlapping_today_utc_total`, `assignments_overlapping_month_utc_total`. Список назначений поддерживает фильтр пересечения периода: query `service_from`, `service_to` (дата ISO), см. `GET /api/v1/fleet/assignments`. При расширении ответа API выкатывайте **бэкенд раньше фронта**, чтобы клиенты не ломались на неизвестных полях.
- **Календарь и список назначений (SPA):** на `/app/fleet/calendar` сетка и дни — **UTC** (как строки дат назначений и агрегаты обзора); в query синхронизированы `view` (`month` \| `week` \| `agenda`), `month` (`YYYY-MM`), `week` (`YYYY-MM-DD`, понедельник недели UTC), фильтры `line_id`, `status`. На `/app/fleet/assignments` — `line_id`, `status`, `service_from`, `service_to`; при переходе с календаря добавляются `cal_view`, `cal_month`, `cal_week` для ссылки «назад в календарь»; после любого изменения query на назначениях при активном `cal_view` поля `cal_month` / `cal_week` выравниваются по текущему диапазону (`service_from`, иначе `service_to`; при очистке дат — `cal_month`/`cal_week` убираются).
- **Дашборд Fleet:** быстрые переходы к календарю и списку назначений для **текущего UTC-дня** и **текущего UTC-месяца** (в одной линии с KPI «Active today (UTC)» / «This month (UTC)»), чтобы совпадать с агрегатами `GET /api/v1/fleet/overview`.
- **Сезонность по линии** строится из данных: `GET /api/v1/fleet/operating-lines/{line_id}/seasonality-from-data` — веса по календарным месяцам из суммы дней пересечения с каждым месяцем окна (`months_back`, по умолчанию 24). Источники: `sources=assignments` (назначения), `sources=roster` (участие водителей с `effective_from`/`effective_to` и ТС на линии с даты членства), либо оба с `weight_assignments` / `weight_roster` (нормализуются к сумме 1). Поле `seasonality_month_factors` у линии в БД — устаревающий ручной override, не основной источник продукта.
- Канонические URL SPA и Python-константы (`spa_paths`): **`shared/crm_app_paths.json`** → `python3 scripts/codegen/generate_crm_app_paths.py` (обновляет `hostflow-frontend/src/app/crmAppPaths.generated.ts` и `backend/app/constants/spa_paths.py`). Включены все сегменты Fleet, в т.ч. **`fleetCalculator`**, плюс legacy-маршруты (`messages`, `communicationsLegacyHub`, `plannerLegacy`, `companiesLegacy`).
