## Критерий

Неподготовленный оператор, начиная с экрана Forms и без знания архитектуры HostFlow, самостоятельно создаёт брендированную форму, добавляет и настраивает поля, сопоставляет ответы с данными HostFlow, смотрит preview, публикует форму, получает hosted URL или код для своего сайта, принимает реальный ответ и видит и исходные ответы, и то, куда они записались. Без разработчика, ручного JSON и работы с базой или API.

FP-1…FP-5 доказывают механизм публикации и public submission. Этот контракт доказывает Forms как self-service продукт. Закрытый Forms Publish contract он не открывает.

## 1. Жизненный цикл

Один сценарий. Маппинг — настройка до публикации, не шаг после каждого ответа. На приёме применяются правила той версии, которую респондент заполнил.

```text
Create → Build → Configure → Map → Preview → Publish
  → Share / Embed → Receive → Review Responses → Use Data
  → Edit → Republish / Unpublish
```

Состояния публикации — проекция уже принятой модели: мутабельный `FormDefinition` (draft) и неизменяемый `FormPublicationVersion`. Параллельный механизм публикации запрещён.

| Состояние | Что видит оператор | Что видит респондент | Что запрещено |
|-----------|--------------------|----------------------|---------------|
| **Draft** | Свободное редактирование, черновик сохраняется | Форма публично недоступна | Публичный URL, embed и submit по draft |
| **Published** | Live, версия, дата, ссылка, embed, Unpublish | Только текущий `FormPublicationVersion` | Отдача live-черновика как опубликованной формы |
| **Draft changes** | Редактирование нового draft при живой публикации | Прежняя опубликованная версия | Запись правок draft в текущий snapshot |
| **Republish** | Следующая версия становится Live | Новый snapshot; старые ссылки на текущий pointer, если не снят с публикации | Перезапись предыдущей строки ledger |
| **Unpublished** | Публичный доступ снят; история и submissions на месте | Отказ, без тихого приёма | Удаление ledger, submissions или consent evidence |

`activate` / `deactivate` адаптера меняют доступность Endpoint и не переписывают snapshot.

Каждый submission хранит `form_id` + `published_version` той версии, которая его приняла. Поздняя версия не переякоряет уже принятый ответ ([`ADR-007`](ADR-007-forms-platform-capability.md), юридический инвариант).

### Запись формы

Публикационные состояния выше описывают, что видит респондент. Запись формы у оператора живёт отдельно.

| Действие | Результат |
|----------|-----------|
| **Duplicate** | Новая форма-черновик: поля, маппинг, тексты согласий, переопределение темы, окно приёма. Новый идентификатор и новый публичный адрес. История версий и ответы не копируются. Компания по умолчанию та же; оператор может выбрать другую до первой публикации копии. |
| **Archive** | Форма уходит из рабочего списка. Если она была Live, публичный доступ прекращается тем же действием. Версии, ответы, файлы и evidence согласия остаются. Новая публикация из архива запрещена. |
| **Restore** | Форма возвращается в список как снятая с публикации, не как Live. Чтобы респондент снова её увидел, нужен Publish. |
| **Delete** | Только у администратора тенанта и только если боевых ответов не было. Тестовые отправки удалению не мешают. Удаляются черновик и версии без ответов. Форма с хотя бы одним боевым ответом не удаляется: для неё путь — Archive. |

Delete формы не является стиранием человека и не заменяет export / erasure / retention платформы ([`ADR-039`](ADR-039-tenant-data-lifecycle.md)). Forms участвует в том жизненном цикле как владелец своих записей, а не заводит вторую кнопку «стереть кандидата».

## 2. Создание

Пустое состояние Forms предлагает два входа: **с нуля** и **из шаблона**. Шаблон — готовая композиция полей и настроек, которую оператор затем правит как обычный draft. Шаблоны не второй каталог типов полей.

Минимум при создании, на языке оператора:

| Поле | Смысл |
|------|--------|
| Название | Как форма называется в списке и, по умолчанию, на публичной странице |
| Внутреннее описание | Зачем форма; респондент его не видит |
| Язык | Язык первой публикации и fallback |
| Тип использования | Бизнес-контекст, см. ниже |
| Компания | Чья форма и чей бренд по умолчанию |

Типы использования, которые оператор выбирает:

- Форма кандидата
- Форма заявки клиента
- Дополнительная анкета кандидата
- Короткий опрос
- Повторная анкета (follow-up)

`route_intent`, Intake Source Profile, Endpoint, provider binding, `entity_profile_code`, `qualified_code` и `component_id` могут существовать внутри. На этом пути они не являются подписями, обязательными полями и текстом ошибок. Если без них форму нельзя создать или опубликовать, это разрыв продукта, а не требование к оператору.

Принадлежность компании выбирается из компаний тенанта. Оператор не вводит slug как идентификатор архитектуры: публичный адрес система предлагает сама, оператор может его поправить понятным коротким именем.

### Смена компании

До первой публикации компанию можно сменить. Превью бренда переключается на тему новой компании. Маппинг не пересобирается: canonical-поля не принадлежат компании.

После первой публикации компания формы неизменна. Каждая publication version и каждый её submission хранят компанию, при которой ответ принят. Смена темы другой компании не перекрашивает эту историю.

Перенести уже опубликованную анкету в другую компанию значит Duplicate в ту компанию и публиковать копию. История исходной формы остаётся на месте.

## 3. Builder

Builder редактирует draft `FormDefinition`. Сохранение draft не вызывает `publish` и не создаёт `FormPublicationVersion` (граница C3).

Обязательные действия с полем:

- добавить из палитры;
- удалить;
- дублировать;
- изменить порядок перетаскиванием;
- обязательное / необязательное;
- label, пояснение (help), placeholder, значение по умолчанию;
- проверка значения;
- варианты ответа там, где тип их имеет;
- видимость и условная логика;
- ширина и положение в строке;
- preview того, что получится у респондента.

Структурные элементы, которые не являются вопросами: заголовок, абзац, разделитель, секция, изображение / логотип. Они входят в snapshot публикации и в renderer. Они **не** являются целями маппинга: у них нет canonical destination. Это следует разделению Field Registry / Entity Profile и layout и не вводит второй словарь полей.

Черновик сохраняется автоматически. Уход со страницы с несохранённым конфликтом ревизии показывает, что серверная копия новее, и даёт перезагрузить её, не затирая чужие правки молча.

Условная логика — правило draft («показать поле, если…»). Она замораживается в publication snapshot вместе со схемой. Она не выбирает модуль-получатель и не подменяет Mapping Authority.

## 4. Каталог типов полей

Типы берёт оператор из Field Catalog. Builder не изобретает тип. Расширение каталога — только совместимое расширение `forms.field_catalog.stdlib.v1` или новый major контракта каталога, не локальный словарь формы.

Для каждого типа ниже одинаковы четыре правила:

1. **Required** — пустой ответ не проходит публикационную схему; необязательное поле может быть пустым.
2. **Пустой ответ** сериализуется как отсутствие значения, не как пустая строка, выданная за введённые данные. Неотвеченное необязательное поле не создаёт canonical write.
3. **Mapping compatibility** задаёт Mapping Authority: форма не решает, что число можно записать в имя.
4. **Mobile и desktop** показывают один и тот же контроль и те же ошибки; отличается только раскладка.

| Тип | Проверка и допустимые значения | Ответ | Маппинг |
|-----|--------------------------------|-------|---------|
| Короткий текст | min/max длина, пустая строка = пусто | строка | текст / имя / код, если профиль разрешает |
| Длинный текст | min/max длина | строка | длинный текст профиля |
| Email | формат адреса | нормализованный адрес | email-поле профиля |
| Телефон | страна и национальный номер; не «любые цифры» | канонический номер | телефон профиля |
| Число | min/max, целое или дробное | число | числовое поле профиля |
| Дата | календарная дата, границы | дата | дата профиля |
| Дата и время | дата, время, зона публикации | instant | дата-время профиля |
| Один из списка | ровно один вариант из списка публикации | выбранный option id | одно значение + option mapping |
| Несколько из списка | ноль или более разрешённых option id | список option id | множественное поле профиля |
| Радио | как один из списка, другой контрол | option id | как single select |
| Чекбокс группы | как несколько из списка, другой контрол | список option id | как multi-select |
| Да / нет | два явных значения, не свободный текст | boolean | boolean профиля |
| Адрес | структура (улица, город, индекс, страна), не одна строка без разбора | структура адреса | адрес профиля |
| Страна | значение из Platform Reference (страна), не локальный список формы | код страны справочника | страна / гражданство профиля |
| Файл / документ | число файлов, размер и допустимый вид файла по §18; сбой загрузки не равен пустому ответу | ссылка на принятый файл | слот документа через контракт Documents, не самодельный тип документа |
| Согласие | не обычный checkbox; см. §10 | evidence принятия | не бизнес-поле анкеты |
| URL | абсолютный http(s) URL | URL | URL-поле профиля |
| Скрытое / системное | значение задаёт форма, респондент его не редактирует | заданное значение | только если профиль явно разрешает скрытый источник |

Варианты select / radio / multi-select хранят стабильный option id и подпись на языке публикации. Маппинг идёт по option id. Перевод подписи не создаёт новое значение (§9).

Телефон, email, даты, файл и согласие не считаются выполненными, если на странице есть только визуальный input без проверки, нормализации и (для согласия) evidence.

## 5. Маппинг

Две разные сущности:

| | Форма | HostFlow |
|--|-------|----------|
| Что это | Вопрос респонденту | Куда ответ должен попасть |
| Пример | Imię, Nazwisko, Telefon, Prawo jazdy | Person → First name, Person → Last name, Person → Phone, Candidate → Driving licence category |
| Кто задаёт | Оператор в Builder | Mapping Authority: canonical field / profile contract |

Оператор настраивает это на самой форме, визуально: вопрос слева, понятное имя поля HostFlow справа. Технический `qualified_code` в этом списке не показывается. Группировка читается как «Кандидат → Категория водительских прав», не как код реестра.

Forms не заводит второй словарь полей и не решает, Recruitment это или Sales. Назначение вытекает из типа использования формы и принятого profile contract. Несовместимый тип — ошибка настройки, не тихая запись.

Обязательные сценарии:

| Ситуация | Поведение |
|----------|-----------|
| Поле без маппинга | Разрешено, если вопрос не объявлен обязательным для записи. Ответ остаётся в submission. В бизнес-сущность не пишется. Оператор видит «не сопоставлено». |
| Обязательный маппинг | Поля, без которых выбранный тип формы не может создать сущность (для формы кандидата — минимум идентичности, который задаёт profile contract), блокируют Publish. |
| Несовместимые типы | Publish не проходит. Оператор видит вопрос и имя поля HostFlow, не внутренний код ошибки. |
| Два вопроса в одно поле | Publish не проходит, пока оператор не оставит один источник или явно не задаст правило слияния, которое уже есть в Mapping Authority. Форма не изобретает своё слияние. |
| Смена маппинга после публикации | Действует со следующей версии. Старые submissions остаются при своём snapshot и своём результате записи. |
| Удаление сопоставленного поля | В новой версии вопроса нет. Старые ответы и уже записанные данные не стираются. |
| Удалённое canonical поле | Publish новой версии не проходит. Уже принятые submissions не переигрываются молча. |
| Option mapping | Каждый вариант вопроса сопоставлен со значением справочника или явно помечен «не записывать». |
| Свой ответ («другое») | Хранится в submission как введённый текст. В canonical поле пишется только если профиль принимает свободное значение; иначе submission остаётся, запись поля — в состоянии, которое оператор видит. |
| Старые submissions после смены формы | Не пересобираются новой схемой. Их версия, сырые ответы и тогдашний результат записи сохраняются. |

## 6. Куда попадает ответ

Цепочка одна, без второй очереди «для embed»:

```text
Public form (hosted или embed)
  → submission принят
  → определены источник и FormPublicationVersion
  → ответы проверены по snapshot этой версии
  → маппинг выполнен по правилам этой версии
  → intake_handoff
  → routing
  → сущность владельца (Candidate, Application, заявка клиента, …)
  → исходный submission остаётся доказательством
```

Сырой submission не удаляется и не заменяется результатом маппинга. Оператор по каждому ответу может ответить:

- кто заполнил (если идентичность известна; иначе — что идентичность не установлена);
- когда;
- какая версия формы;
- какие ответы даны, в формулировках той версии;
- куда данные записаны;
- создалась ли ожидаемая сущность;
- если нет — почему, и что сделать.

Несозданный Candidate без записи на форме — разрыв контракта, даже если строка есть в базе.

## 7. Способы использования

| Поверхность | В этом контракте | Правило |
|-------------|------------------|---------|
| **Hosted** | Обязательна для приёмки | `…/form/…` или текущий публичный путь, который отдаёт **тот же** frozen snapshot |
| **Embed** | Обязательна для приёмки | Фрагмент для сайта клиента (`iframe` и короткий snippet). Тот же snapshot, тот же renderer, тот же submit |
| API, webhook, портал | Зафиксированы как будущие поверхности | Не входят в приёмку этого gate и не получают отдельный движок формы |

Embed не хранит свою копию схемы и не принимает ответы мимо `forms.public_contract.v1`. Снятие с публикации гасит и ссылку, и embed.

Hosted URL, который оператор копирует, открывает опубликованную версию, а не текущий draft и не отдельное presentation-определение формы.

## 8. Брендирование

Наследование:

```text
Тема компании (logo, цвета, название, ссылки)
  → переопределение на форме, только там, где оператор его задал
```

Оператор не брендирует каждую новую форму заново. Первая форма компании выглядит как компания.

На форме можно задать: логотип, основной и акцентный цвет, фон, политику шрифта в пределах платформы, стиль рамки и кнопки, название компании, favicon, верхний и нижний колонтитул, экран успеха, произвольный текст успеха, ссылки на политику конфиденциальности и условия.

«Powered by HostFlow» — коммерческая политика, не отдельный движок. Архитектура формы умеет показать или скрыть эту строку. Кто имеет право скрыть, задаёт тариф: в [`ADR-007`](ADR-007-forms-platform-capability.md) брендирование относится к Advanced. Этот контракт не вводит новый тариф.

Тема замораживается в publication snapshot вместе со схемой. Смена темы компании не перекрашивает уже принятые доказательства согласия и не меняет задним числом отданную версию; новая публикация или явная политика «живая тема компании» должна быть названа в UI. По умолчанию респондент видит тему той версии, которую открыл.

## 9. Локализация

Одна публикация может нести переводы. Отдельная форма на каждый язык не требуется.

Переводятся: labels, пояснения, варианты, ошибки, тексты согласий, экран успеха. Не переводится: option id, canonical value, маппинг.

«Prawo jazdy CE», «Водительское удостоверение CE» и «CE driving licence» — три подписи одного option id и одного canonical value.

Язык выбирается из языка ссылки, затем из языка браузера, затем из fallback-языка формы. Нет перевода строки — показывается fallback, не ключ и не `qualified_code`.

Маппинг не зависит от языка сессии.

---

## 10. Согласие

Согласие — отдельный контракт, не `forms.field.checkbox`.

У каждого согласия есть: текст, версия текста, обязательность, ссылки на Privacy Policy и Terms, которые действовали в момент публикации. При принятии submission хранит: факт принятия, время, версию текста, `published_version` формы и ссылки, показанные респонденту.

Смена текста после публикации не переписывает evidence старых submissions. Новый текст попадает к респондентам только со следующей publication version (`consent_pin` на строке ledger, уже предусмотренный `commit_publish`).

Обязательное согласие без принятия не создаёт бизнес-сущность и не теряет попытку: оператор видит отказ проверки, а не пустой список ответов.

## 11. Preview и тест

До Publish оператор имеет:

- preview на ширине desktop;
- preview на ширине mobile;
- прохождение формы как респондент (test submission).

Test submission идёт по той же схеме draft, которую оператор собирается публиковать, и **не** создаёт Candidate, Application, Lead и не запускает боевой routing. Результат теста помечен как тест и виден оператору отдельно от Responses. Публичная ссылка и кнопка «Открыть форму» — это боевая форма, не замена теста.

---

## 12. Publish

Publish — одно бизнес-действие. Оператор не выбирает ledger, snapshot и adapter.

Перед записью версии система проверяет и, при провале, останавливает публикацию:

- ошибки полей и проверок;
- обязательные настройки формы (название, язык, тип, компания);
- маппинг (§5);
- согласие (§10);
- окно приёма, если оно задано (§19);
- ограничения файлов (§18);
- контраст темы (§21);
- готовность приёма для выбранного типа использования (источник и маршрут уже связаны внутри; оператор видит «куда попадут ответы», не `route_intent`).

После успеха оператор видит:

- Live;
- публичный URL, копирование, открытие;
- код embed;
- QR — по желанию, не условие приёмки;
- номер версии и дату публикации;
- Unpublish.

Повторный Publish с тем же идемпотентным ключом не плодит вторую версию (уже есть у `commit_publish`). Осмысленное изменение draft и новое подтверждение создают следующую версию.

---

## 13. Правка опубликованной формы

Оператор открывает опубликованную форму → Edit. Правки идут в draft. Респондент по-прежнему видит прежнюю версию. Preview показывает draft. **Publish changes** создаёт следующую `FormPublicationVersion`.

```text
Submission A → V1
Submission B → V1
Submission C → V2
```

**Откат.** Вернуть V1 значит опубликовать новую версию, снимок которой равен снимку V1. Старая строка ledger не реактивируется и не редактируется (`forms_publication_version_immutable`). В истории это Vn с пометкой, что содержание восстановлено из V1. Submissions, принятые V1, остаются привязаны к V1.

Unpublish после отката не требуется, чтобы «выключить» промежуточные версии: текущий pointer и есть то, что отдаётся. Промежуточные версии остаются читаемыми для своих submissions.

## 14. Ответы

Появления Candidate в Recruitment недостаточно.

```text
Forms → Form → Responses
```

В списке: дата, статус, респондент (если известен), состояние записи (сопоставлено / не сопоставлено / ошибка / нужно действие), куда записано. Открытие ответа показывает исходные ответы версии, которая их приняла, и результат записи. Персональные ответы и файлы видны только с правом на персональные данные (§17).

На списке форм и на шапке формы оператор видит рабочие счётчики, и это не Analytics:

- состояние: черновик, Live, снята, архив;
- число боевых ответов;
- число ответов в **Action required**;
- время последнего боевого ответа.

Тестовые отправки в эти числа не входят. Конверсия, брошенные шаги, время заполнения и окупаемость источника остаются P5 и в этот контракт не входят.

Пустой список при живой ссылке — допустимое состояние «ответов ещё нет», и оно отличимо от «приём выключен», от «окно закрыто / лимит исчерпан» и от «ответы были, запись не удалась».

## 15. Ошибки

Приём устроен fail-closed: сомнительный ответ не объявляется успешно обработанным.

| Ситуация | Что происходит |
|----------|----------------|
| Невалидный маппинг на Publish | Публикация не выполняется |
| Canonical поле удалено | Новая публикация не выполняется; старые ответы на месте |
| Получатель недоступен | Submission сохранён, статус **Received — Action required** |
| Дубликат человека | Submission сохранён; оператор видит, с кем совпало, и может открыть существующую карточку |
| Повторная отправка того же ответа | Один submission, не две сущности |
| Срок окна истёк, лимит ответов исчерпан или форма снята | Респондент видит отказ; успешная запись не создаётся (§19) |
| Сбой загрузки файла | Ответ не считается принятым, пока обязательный файл не принят; частичный файл не выдаётся за документ (§18) |
| Спам / проверка человека не пройдена или проверка недоступна | Отказ до создания сущности; повтор после успешной проверки не теряет введённые ответы (§20) |
| Сбой сети и повтор | Повтор с тем же ключом не создаёт второй submission |
| Двойной клик Submit | Один submission |
| Частичная обработка | Submission в **Received — Action required**, с причиной и уже выполненным шагом |
| Маршрут не разрешён | Сущность не создаётся молча; статус и причина видны на форме |

Submission нельзя потерять молча. Отсутствие кандидата без строки ответа — дефект.

## 16. Экран после отправки

Респондент всегда получает подтверждение по версии, которую он отправил.

По умолчанию — короткий текст успеха на языке этой сессии. Оператор может задать заголовок и текст; они переводятся так же, как остальные строки формы (§9), и замораживаются в snapshot.

Необязательный переход на другой адрес: только `https`. Сначала респондент видит подтверждение, затем переход. Адрес без `https` публикацию не проходит.

Экран успеха использует тему опубликованной версии. Он не показывает внутренние идентификаторы, коды полей и состояние маппинга.

Респондент не редактирует уже принятый ответ. Исправление — новая отправка, если форма всё ещё принимает ответы; прежний submission остаётся.

## 17. Кто что может

Права — четыре trust role [`ADR-036`](ADR-036-four-trust-roles-rbac.md) и выдачи на компанию. Пятая роль «редактор форм» не вводится. Выдача на компанию A не открывает формы и персональные данные компании B.

| Действие | Администратор тенанта | Сотрудник с выдачей на эту компанию | Viewer |
|----------|----------------------|--------------------------------------|--------|
| Создать, править draft, дублировать, маппить, смотреть preview и тест | да | да, если в выдаче есть правка форм | нет |
| Publish, Republish, Unpublish, Archive, Restore | да | да, если в выдаче есть публикация | нет |
| Delete по правилу §1 | да | нет | нет |
| Видеть список Responses и счётчики §14 | да | да, если в выдаче есть просмотр ответов | нет |
| Видеть значения ответов и скачивать файлы | да | да, только с отдельной выдачей на персональные данные | нет |
| Менять тему компании и выключать защиту от спама | да | нет | нет |

`superadmin` — платформенная поддержка, не оператор компании в этом сценарии. Публичный респондент не аутентифицирован и не получает ни одного из этих прав.

Имена permission-ключей при реализации берутся из паспорта Forms. Этот контракт задаёт действия и границу персональных данных, а не второй RBAC.

## 18. Файлы

Поле файла задаёт ограничения, и они замораживаются в publication version:

- сколько файлов на поле (по умолчанию один);
- максимальный размер одного файла — не выше платформенного потолка; оператор может только снизить его;
- допустимый вид файла из закрытого списка (изображения, PDF, офисные документы), не произвольная строка MIME, придуманная формой.

Хранение, проверка типа, скачивание и срок хранения — Documents ([`ADR-009`](ADR-009-document-hub-platform-layer.md)). Forms не держит второе файловое хранилище и не задаёт свой TTL мимо retention платформы ([`ADR-039`](ADR-039-tenant-data-lifecycle.md)).

Скачивание файла из ответа — то же право, что и просмотр персональных данных (§17). Респонденту после отправки ссылка на файл обратно не выдаётся.

Файл сверх лимита или недопустимого вида не принимается. Обязательное поле без принятого файла не создаёт успешный submission.

## 19. Окно приёма

Это часть продукта, не отложенный режим.

На публикации можно задать:

- момент открытия;
- момент закрытия;
- максимальное число боевых ответов этой версии.

Числа и даты входят в snapshot. Сдвинуть их — Republish. Остановить приём немедленно, не меняя схему, — Unpublish.

Счётчик боевых ответов — runtime этой версии. Тесты в него не входят. Когда лимит достигнут, версия остаётся в истории, но новые ответы не принимает, даже если форма ещё не снята с публикации.

До открытия, после закрытия и при исчерпанном лимите респондент видит, что форма сейчас не принимает ответы. Успешный submission не создаётся.

## 20. Защита от спама

Политика принадлежит Forms ([`ADR-028`](ADR-028-configuration-ownership.md): CAPTCHA — Configures Forms). Исполнение — уже существующие платформенные rate limit и Turnstile. Второй CAPTCHA-продукт и отдельный антиспам-движок формы не создаются.

По умолчанию у компании оба контроля включены, и новая форма их наследует. Выключить защиту на форме может только администратор тенанта.

Скрытое поле-ловушка допустимо как приём renderer. Оператор его не настраивает как вопрос, и оно не является целью маппинга.

Если rate limit или проверка человека не могут выполниться, ответ не принимается. Респондент может повторить попытку. Недоступный Redis не означает тихий приём.

## 21. Доступность публичной формы

Публичный renderer, hosted и embed, целится в WCAG 2.2 уровня AA.

- У каждого поля есть видимая подпись. Placeholder подписью не считается.
- Ошибка написана текстом и связана с полем.
- Вся форма, включая выбор, файл и согласие, проходит с клавиатуры. Порядок фокуса совпадает с порядком на экране.
- Язык страницы — язык сессии.
- Тема, которая не держит контраст AA, не публикуется: проверка входа в Publish, не предупреждение после факта.

## 22. Уведомления

Новый ответ оператор узнаёт из Responses. Это источник истины Forms.

Доставка «пришёл ответ» (колокол, письмо, тихие часы, шаблон, кому слать) — Notifications, не экран Forms ([`ADR-028`](ADR-028-configuration-ownership.md)). Forms может отдать факт «submission принят», на который Notifications подписывается. Отсутствие письма не означает потерянный ответ, если строка есть в Responses.

Для приёмки этого контракта письмо и колокол не требуются.

## 23. Что этот контракт не делает

- Не объявляет FP-1…FP-5 выполненными и не ставит их в очередь.
- Не переносит P5 Analytics в объём этого продукта. Рабочие счётчики §14 — не дашборд. Бренд здесь — требование операторского продукта; P4 как программа тем остаётся отдельным именем в каноне и не получает второй движок темы.
- Не мигрирует `TenantLeadForm` в FormTemplate SoT и не добавляет нового писателя в storage bridge.
- Не создаёт второй submit, второй renderer для embed, второй словарь полей, второй RBAC и второе хранилище файлов.
- Не заменяет [Release Readiness Gate](../gates/release-readiness-gate.md). Этот gate может быть PASS, а v1 всё ещё не release-ready.
- Не описывает многошаговый мастер: публичная форма — одна страница, секции только группируют поля.
- Не даёт респонденту черновик «продолжить позже» и не даёт ему править принятый ответ.
- Не включает внутреннюю форму для уже вошедшего сотрудника как поверхность приёмки. Тот же snapshot и тот же submit могут появиться позже; отдельный движок для неё запрещён заранее.
- Не включает выгрузку ответов файлом, воронки и API/webhook как поверхность приёмки.
- Не делает письмо или колокол обязательными (§22).

## Полнота контракта

Проверка 2026-09-22, после дополнения. Вопрос один: описан ли законченный операторский продукт, или после PASS по F-01…F-16 снова всплывёт дыра.

| Тема | Где закрыта |
|------|-------------|
| Порядок: маппинг до Publish, применение при Receive | §1 |
| Права, персональные данные, граница компании | §17 |
| Duplicate, archive, restore, delete | §1, запись формы |
| Смена компании | §2 |
| Окно и лимит ответов | §19 |
| Экран успеха и запрет правки ответа | §16 |
| Файлы: число, размер, вид, доступ, retention | §18 |
| Спам: кто включает, чем исполняется, fail-closed | §20 |
| Клавиатура, подписи, ошибки, WCAG 2.2 AA | §21 |
| Счётчики без P5 | §14 |
| Уведомление оператора | §22: факт можно отдать, доставка вне Forms |

Явно вне продукта, чтобы freeze их не прятал: многошаговый мастер, черновик респондента, правка принятого ответа, внутренняя форма как отдельная приёмка, файловая выгрузка и дашборды, обязательные письмо и колокол, стирание человека кнопкой Delete (§23, [`ADR-039`](ADR-039-tenant-data-lifecycle.md)).

**Итог проверки: PASS.** Текст описывает законченный операторский продукт. Contract Freeze этим не ставится: статус остаётся **Proposed / freeze-ready**. Проверка не измеряет код, не двигает F-01…F-16 и не добавляет F-17…

Дополнение спецификации не улучшает состояние продукта. Матрица приёмки меняется только новым замером дерева, не правкой этого документа.

За границей freeze, и их отсутствие не мешает будущему PASS приёмки: многошаговый мастер, черновик респондента, внутренняя форма как отдельная приёмка, выгрузка ответов, стирание человека. Они названы в §23 и не входят в критерий.

**Следующее действие — только после freeze.** Не ещё один архитектурный аудит. Декомпозиция реализации по замороженному контракту: каждый срез закрывает конкретные F-требования и продвигает один путь

```text
Create → Build → Configure → Map → Preview → Publish
  → Share / Embed → Receive → Review Responses → Use Data
  → Edit → Republish / Unpublish
```

До freeze срезы не открываются, F-01…F-16 не закрываются и не расширяются.
