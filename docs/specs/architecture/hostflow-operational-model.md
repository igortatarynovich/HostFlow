# HostFlow Operational Model

**Status:** canonical (L1) — **конституция продукта** (правила, по которым разрешено развивать HostFlow).  
**Owner:** Product + Platform UX + Architecture.

**Девиз:** *Тогда не возникает вопроса «как».*

---

## Цель

> **Исключить повторное проектирование уже решённых задач.**

Если для новой функции снова нужно решать, **как** она выглядит, **как** ведёт себя или **как** взаимодействует с пользователем — operational model **нарушена** или требует **осознанного расширения** (§0 + ADR).

Разработчик получает задачу и спрашивает только:

**Что должно делать приложение?**

На «как» отвечает платформа.

**Уровень:** HostFlow строит не только архитектуру **системы**, но и архитектуру **принятия решений**. Вопрос «как сделать модуль HR?» заменяется на «как принимается решение, как должен выглядеть HR?» — ответ уже в этом документе и Platform Standards.

---

## Иерархия документов

**Архитектура и код — следствие.** Сначала operational model; implementation подчиняется ей, не наоборот.

```text
                    Operational Model
              «Как вообще работает HostFlow?»
                              │
                    Platform Standards
         «Как реализуются принципы?» (ADR-010, 011, 017, …)
                              │
                   Module Specifications
              «Что делает конкретный модуль?»
                              │
              ┌───────────────┴───────────────┐
              │  Implementation (производные)  │
              │  API · data models · UI ·       │
              │  components · tests             │
              └───────────────────────────────┘
```

| Уровень | Вопрос | Примеры |
|---------|--------|---------|
| **Operational Model** | Как пользователь работает? | §3 — рабочая сущность, blockers, next action |
| **UI Constitution v1** | Какие объекты в UI? Lead ban? | [`ui-constitution-v1.md`](ui-constitution-v1.md) — product surface |
| **HostFlow Platform Canon v1** | Как строится любой UI? | [`hostflow-platform-canon-v1.md`](hostflow-platform-canon-v1.md) — five layers, canon-first rule |
| **Platform Standards** | Как это реализовано? | [`ADR-010`](ADR-010-unified-resource-list-shell.md), [`ADR-011`](ADR-011-hostflow-ui-platform-standard.md), [`ADR-017`](ADR-017-workspace-layer.md), Document Hub, Forms, Activity |
| **Module Specifications** | Что уникально в домене? | Fleet: лицензии, назначение; HR: контракт |
| **Implementation** | Как закодировать? | OpenAPI, models, React, pytest |

ADR **не отправная точка** — platform standards, выведенные из operational model. Обзор связки ADR: [`hostflow-interaction-architecture.md`](hostflow-interaction-architecture.md).

**Роли документов:**

| Документ | Роль |
|----------|------|
| **Operational Model** | Конституция — что разрешено, как принимаются решения |
| **Platform Standards (ADR)** | Законы — механизм реализации |
| **Module Specifications** | Регламенты модуля — domain |
| **Code + tests** | Исполнение |

**Назначение этого документа:** зафиксировать **единый способ работы** с любой сущностью HostFlow — не React, не backend, не «Shell».

## Порядок принятия решений

Любая задача (feature, модуль, PR) проходит **одну цепочку**. Пропуск шага = архитектурный дрейф.

```text
1. Operational Model     →  соответствует §3?  да → применяем; нет → обоснование + изменение модели
2. Platform Standards    →  есть ADR/capability?  да → следуем; нет → ADR на platform layer
3. Module Specification  →  только domain: данные, rules, actions, API
4. Implementation        →  код, UI, тесты
```

| Шаг | Вопрос | Если «нет» |
|-----|--------|------------|
| **1** | Покрывает ли operational model сценарий? | PR **не стартует** без изменения этого документа (§0.1) |
| **2** | Есть platform standard (ADR-010, 011, 017, …)? | ADR / расширение standard — **до** module PR |
| **3** | Что domain-specific? | Module spec + API |
| **4** | Как реализовать? | Код по standards |

**Review gate:** PR указывает, какое решение взято с шага 1–2. «Сделали по-своему» без шага 1–2 — reject.

### Документация → код (не наоборот)

Документация — **источник решений**, не описание уже написанного кода.

```text
Operational Model  →  принимает решение «как работает»
Platform Standard  →  описывает механизм реализации (ADR)
Module spec + Code →  реализует ADR
Tests              →  подтверждает реализацию
```

Идея **сначала в коде**, минуя operational model / ADR — **нарушение процесса** (архитектурный долг с первого дня).

## 0. Meta-rule (выше Platform Standards)

> **Любое новое решение сначала использует существующую операционную модель. Новое поведение допускается только если модель объективно не покрывает сценарий — с явным обоснованием в PR/spec.**

### 0.1 Единственная точка входа для новых паттернов

> **Operational Model — единственное место, где допускается новый пользовательский паттерн.**

Новая модель карточки, тип экрана, способ blockers/confirm/navigation — **не начинается с PR**. Сначала изменение operational model (+ при необходимости Platform Standard ADR). Не прошло сюда — **не появляется в продукте**.

| Хотят в PR | Правильный первый шаг |
|------------|------------------------|
| Новая «карточка» / layout сущности | §3 + ADR-017 |
| Новый способ blockers / next action | §3.1, §4 |
| Новый confirm / error UX | ADR-011 (шаг 2) |
| Новая навигация по коллекции | ADR-010 (шаг 2) |
| Принципиально новый interaction | **PR на этот документ** → потом ADR → потом module PR |

**Gate для нового паттерна:**

| Вопрос | Если ответ «нет» → новый паттерн не нужен |
|--------|---------------------------------------------|
| Можно открыть сущность через list (ADR-010) + §3.2? | |
| Документы — через Document Hub? | |
| Требования / compliance — через Requirement Engine? | |
| Blockers + next action — через status zone §3.1? | |
| История — через Activity/Timeline? | |
| UI — через ADR-011 компоненты? | |

**Пример:** «Для Fleet сделаем особую карточку» → **Почему operational model не подходит?** Нет ответа → водитель по §3, обсуждаем только fleet-specific data и rules.

Расширение модели (новая зона, новый контракт) — **отдельное ADR**, не локальное исключение в одном PR.

### 0.2 Обратимость к Operational Model («почему?»)

> **Любое продуктовое решение должно быть обратимо к Operational Model или Platform Standard.**

На вопрос **«почему так?»** — ответ со ссылкой на раздел этого документа или ADR:

| Вопрос | Допустимый ответ |
|--------|------------------|
| Почему blockers справа? | §3.2 — status zone |
| Почему действия в header? | §3.2 — primary actions |
| Почему confirm такой? | ADR-011 — platform standard, шаг 2 |
| Почему список с фильтрами? | ADR-010 |

**Признак архитектурного долга** — ответы:

- «Так исторически сложилось»
- «Так было проще сделать»
- «Так решил разработчик»

### 0.3 Критерий review (один вопрос)

> **Можно ли объяснить решение, не выходя за рамки Operational Model (+ Platform Standards)?**

| Ответ | Действие |
|-------|----------|
| **Да** | Решение естественно вписывается — можно реализовывать |
| **Нет, но нужен новый паттерн** | Осознанное расширение §0.1 → ADR → код |
| **Нет, и паттерн не нужен** | Reject — не соответствует архитектуре продукта |

**Пример (Step 5):** отдельный `/requirements` экран **не выводился** из operational model — его приходилось объяснять отдельно (второй status rail, «открыть workspace»). Spike допустим для проверки контрактов; product path — section внутри карточки по §3.

### 0.4 Два разных решения = модель недостаточна

> **Если два опытных разработчика независимо пришли к разным UX-решениям одной задачи — Operational Model недостаточно определён.**

**Исправляется не код** (унификация экранов post-factum), **а этот документ** — чтобы следующий разработчик **не мог** выбрать другое решение.

| Симптом | Неправильная реакция | Правильная реакция |
|---------|----------------------|-------------------|
| Два PR с разным layout одной сущности | «Выберем лучший в merge» | Уточнить §3 / Forbidden; закрыть двусмысленность |
| Спор «где blockers» без ссылки на doc | Компромисс в UI | Дописать operational model |
| «Каждый модуль по-своему» | Рефакторинг через год | §0.1 + Forbidden |

Зрелая платформа **не полагается на опыт людей** — сужает пространство интерпретации.

## 1. Главный принцип

> **HostFlow — операционная система бизнеса, а не набор модулей.**

Модули (Recruitment, HR, Fleet, Finance, Services) реализуют **бизнес-логику своей области**.  
**Способ работы пользователя** — один для всей платформы.

| Стандартизируем | Не стандартизируем |
|-----------------|-------------------|
| Поведение кнопки, таблицы, rail, формы | Уникальный CSS каждого экрана |
| Вопросы, на которые отвечает любая сущность | Один экран для всех ролей |
| Ритм: прочитать → понять блокер → выполнить действие | Склейка модулей в один UI для одного человека |

**Роли изолированы по продукту:** рекрутер работает в Recruitment, HR — в HR, диспетчер — в Fleet. Им **не нужен** «бесшовный переход между модулями». Им нужен **один профессиональный язык** внутри своего модуля — и узнаваемый HostFlow везде.

## 2. Зачем это инженерно

Operational model даёт **два** эффекта — их не путать:

| Эффект | Что уменьшается |
|--------|-----------------|
| **Меньше хаоса в UI** | Десять вариантов таблицы, rail, confirm через 2 года |
| **Меньше архитектурных решений** | Количество раз, когда команда **заново проектирует** interaction |

Второй эффект важнее для платформы: решения принимаются **один раз**, дальше только **применение**.

### 2.1 Что не обсуждается при новом модуле

**Задача:** добавить Fleet.

| В обычном проекте (не должно быть в HostFlow) | Уже решено в |
|-----------------------------------------------|--------------|
| Как выглядит список? | ADR-010 |
| Как выглядит карточка / запись? | §3 |
| Как открываются документы? | Document Hub + §3 |
| Где действия, blockers, история? | §3.1–3.2 |
| Поиск, фильтры, confirm, ошибки? | ADR-010, ADR-011 |

**Обсуждается только предметная область:**

- какие данные у водителя / ТС;
- какие документы и требования специфичны для Fleet;
- какие действия и business rules;
- gates и blockers **по смыслу домена**, не по layout.

### 2.2 Принцип нового модуля

> **Каждый новый модуль приносит новую бизнес-ценность, а не новую модель взаимодействия.**

Новый interaction pattern = нарушение §0, пока не оформлено расширение operational model.

### 2.3 Типовые вопросы «как» — закрыты

| Вопрос (не должен обсуждаться каждый раз) | Ответ уже в |
|---------------------------------------------|-------------|
| Как сделать таблицу? | ADR-010 |
| Как открыть детали записи? | §3.2 + ADR-010 |
| Где ошибки и disabled? | ADR-011 + §4.2 |
| Где primary actions? | Header §3.2 |
| Где blockers и next action? | Status §3.1 |
| Как подтверждать destructive action? | ADR-011 |

**Для пользователя:** один раз научился — работает в любом модуле.  
**Для команды:** половина времени на новый модуль — **не** проектирование UI, а domain + API + declarations.

## 3. Рабочая сущность — единая модель

**Рабочая сущность** — запись, с которой оператор работает после выбора из списка: кандидат, сотрудник, автомобиль, клиент, вакансия, заказ, счёт.

Не «Candidate Workspace» / «Employee Workspace» как разные продукты. **Одна операционная модель.** Меняются данные и domain rules модуля.

### 3.1 Вопросы

| # | Вопрос пользователя | Зона UI | Источник данных |
|---|---------------------|---------|-----------------|
| 1 | **Что это?** | Header, identity | Модуль |
| 2 | **В каком состоянии?** | Summary, status badges | Модуль (+ computed readiness) |
| 3 | **Что уже сделано?** | Sections, progress | Модуль |
| 4 | **Что мешает?** | Status → blockers | Модуль (Requirement Engine, gates, …) |
| 5 | **Что делать дальше?** | Status → next action | **Модуль решает**; платформа **показывает** |
| 6 | **Что произошло?** | Timeline, Activity, audit | Platform Activity + модуль |

### 3.2 Зоны экрана

```text
┌─────────────────────────────────────────────────────────────┐
│ HEADER — что это, ключевой контекст, primary actions         │
├──────────────┬──────────────────────────────┬─────────────────┤
│ SECTIONS     │ WORK AREA                    │ STATUS          │
│ (navigation) │ информация / требования /    │ blockers        │
│              │ документы / domain content     │ readiness       │
│              │                              │ next action     │
├──────────────┴──────────────────────────────┴─────────────────┤
│ TIMELINE / ACTIVITY — что произошло                          │
└─────────────────────────────────────────────────────────────┘
```

Layout может отличаться (tabs vs sidebar). **Семантика зон** — фиксирована.

### 3.3 Примеры

| Модуль | Сущность | Work area (пример) | Blockers (пример) | Next action (пример) |
|--------|----------|--------------------|-------------------|----------------------|
| Recruitment | Кандидат | checklist требований | открытый паспорт | «Загрузить паспорт» |
| HR | Сотрудник | verification items | не подтверждён контракт | «Подтвердить договор» |
| Fleet | Водитель / ТС | compliance items | просрочен осмотр | «Запланировать осмотр» |
| Finance | Счёт | billing lines | неоплачен депозит | «Выставить счёт» |

## 4. Операционные правила (обязательные)

1. **Единая модель сущности** — любая рабочая запись отвечает на вопросы §3.1; нет «особых» карточек без blockers/next action там, где есть процесс.

2. **Действие с понятной причиной** — кнопка/disabled state объясняет **почему** (blocker text), не молчаливый 409.

3. **Blocker → следующий шаг** — каждый blocker **ссылается** на конкретное место или действие; не абстрактное «ошибка валидации».

4. **Status вычисляется** — readiness/stage gates из правил и данных; оператор **не вводит** «готовность» вручную (исключения — явный audit override с правом).

5. **Подтверждение меняет состояние предсказуемо** — после действия UI отражает новый status; idempotent API; повторное действие безопасно или явно запрещено.

6. **Модуль следует модели, не ломает её** — модуль поставляет sections + readiness + actions через контракты ([`ADR-017`](ADR-017-workspace-layer.md), [`workspace-layer-contracts-p0.md`](../platform/workspace-layer-contracts-p0.md)); не рисует второй status rail на отдельной странице.

## Forbidden

Продукты деградируют не от «плохих решений», а от **накопления малых исключений**. Ниже — **запрещено** без §0.1 (изменение operational model) + ADR.

| # | Forbidden | Типичная отговорка (reject) |
|---|-----------|----------------------------|
| F1 | **Новый UX-паттерн** без изменения Operational Model | «Сделаем немного по-другому» |
| F2 | **Новый layout сущности**, если §3 покрывает сценарий | «Для этого модуля удобнее отдельный экран» |
| F3 | **Дублирование** status rail, blockers, next action, confirm | «Временно второй экран» |
| F4 | **Локальный UI**, противоречащий Platform Standards | «Это особый случай» |
| F5 | **Бизнес-логика в UI** (gates, readiness, next action computation) | «Быстрее на фронте» |
| F6 | **Поведение без traceability** — нельзя сослаться на §3 или ADR (§0.2) | «Пока так, потом приведём» |
| F7 | **«Временно»** без ticket на приведение к model + deadline | «Потом refactor» |

**Правило:** «временно» без изменения model = **Forbidden F7**. Через два года пятьдесят «временно» = новый продукт внутри продукта.

**Review:** PR с любым F1–F7 → reject или split: сначала doc/ADR, потом код.

## 5. Стандартизация поведения (не только внешний вид)

### 5.1 Компоненты (ADR-011)

Стандарт — **поведение**, не только цвет:

| Компонент | Одинаково везде |
|-----------|-----------------|
| **Button** | placement primary/secondary, loading, disabled + reason, confirm flow, error feedback |
| **Table / List** | sort, filter, search, bulk select, row actions, empty/loading states, side panel pattern |
| **Form field** | label, validation message, required marker, read-only vs edit |
| **Status rail** | blockers list, one next action, severity colors (tokens) |
| **Timeline** | actor, timestamp, entity link, filter by type |

Детали токенов и PR checklist — [`ADR-011`](ADR-011-hostflow-ui-platform-standard.md).

### 5.2 Коллекции (ADR-010)

Пользователь **один раз** учится работать со списком HostFlow — дальше любой модуль:

- единый list shell (toolbar, filters, columns, pagination);
- open row → рабочая сущность §3;
- saved views где применимо.

### 5.3 Запись (ADR-017)

Контракты platform layer реализуют §3 на конкретном экране модуля:

- `SectionDeclaration` → sections / work area;
- `ReadinessContribution` → status;
- `NextActionDeclaration` → next action;
- capability renderer → body секции.

**Эволюция, не замена:** существующие карточки (Candidate Card, HR Dossier) **приводятся** к модели; новый «Shell» поверх — запрещён (см. Step 5 lesson в ADR-017).

## 6. Platform capabilities в операционной модели

| Capability | Роль в модели |
|------------|---------------|
| **Requirement Engine** | «Требования» + blockers + evidence (Recruitment, HR, Fleet compliance) |
| **Document Hub** | «Документы» в work area; файлы не дублируются между модулями |
| **Activity / Timeline** | «Что произошло» |
| **Forms** | Стандартный input для закрытия data-requirements |
| **Process Engine** | Gates между этапами; blockers отражают PE state |
| **Handoff** | **Platform continuity данных** между модулями — не единый экран для рекрутера и HR |

## 7. Чеклист для UI / PR

**Порядок:** шаги 1–2 («Порядок принятия решений») — **до** кода.

**§0.3:** объяснимо из operational model?

**§0.2:** «почему?» → §3 / ADR, не «исторически».

**Forbidden F1–F7:** нет без doc/ADR.

Любой экран рабочей сущности:

- [ ] Header отвечает «что это?»
- [ ] Status показывает blockers + **одно** next action (если применимо)
- [ ] Blockers кликабельны / ведут к месту исправления
- [ ] Disabled primary action **объясняет** причину
- [ ] Timeline/Activity доступны или явно N/A с причиной
- [ ] Нет второй страницы с дублем status rail
- [ ] Таблицы/кнопки/формы — ADR-010 / ADR-011
- [ ] Domain logic только в модуле/API — не в composition layer

## 8. Связь с lifecycle

## 10. Operational Model Maturity Test

Перед принятием **нового функционала** (spec / epic / крупный PR) — пять вопросов. Не новое правило; **проверка зрелости**.

| # | Вопрос | Ожидание |
|---|--------|----------|
| 1 | Можно реализовать **без нового UX-паттерна**? | Да → §3 + существующие standards |
| 2 | Используются **существующие Platform Standards**? | Да → ADR-010 / 011 / 017 / capabilities |
| 3 | Добавляется только **бизнес-ценность**, не новый способ работы? | Да → domain delta |
| 4 | Все решения **объяснимы** ссылкой на Operational Model и ADR? | Да → §0.2 |
| 5 | Другой разработчик через 5 лет с **той же задачей** придёт к **тому же** решению? | Да → модель достаточно определена |

**Все «да»** — модель работает; можно в implementation.  
**Любое «нет»** — не код первым: уточнить model (§0.1), ADR, или Forbidden.

## 11. Эволюция документа (freeze)

**Статус на 2026-07-03:** модель **завершена для текущего этапа**. Не добавлять новые правила «на всякий случай» — риск **перестандартизации**.

**Как развивается конституция:**

1. **Несколько недель** — все новые идеи **проходят через** этот документ, **без** его расширения.
2. Если большинство вопросов закрывается **без правок** — уровень абстракции правильный.
3. **Расширять только** когда практика (review, Maturity Test, §0.4) **регулярно** показывает gap, которого нет в §0–§Forbidden.
4. Расширение = **точечное** изменение + changelog; не энциклопедия всех случаев.

Порядок решений, review gates, traceability, Forbidden и Maturity Test уже покрывают: *зачем*, *как решать*, *как ревьюить*, *как расти*.

**Карта эволюции (не compliance):** где продукт уже соответствует модели, что в переходе и куда мигрировать — [`operational-model-adoption-register.md`](operational-model-adoption-register.md) (L2). Конституция не расширяется строками про legacy surfaces.
