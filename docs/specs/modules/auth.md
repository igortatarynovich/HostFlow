# Auth Module — Specification

Модуль аутентификации и авторизации (Auth) отвечает за управление пользователями, ролями, токенами и безопасным доступом к данным внутри системы HostFlow. Он является основным элементом RBAC и обеспечивает работу многоарендности (multi-tenancy) на уровне backend и API.

---

## Назначение
- Обеспечить безопасную авторизацию пользователей через JWT.
- Гарантировать разграничение прав доступа по ролям и tenant.
- Поддерживать аутентификацию через email + пароль и внешние токены (например, API keys).
- Обеспечить механизмы refresh-токенов и logout.
- Поддерживать будущие расширения — OAuth2 и SSO.

---

## Основные компоненты
| Компонент | Назначение |
|------------|------------|
| **User** | Модель пользователя. Содержит email, hashed_password, role, tenant_id, is_active, extra. |
| **UserInvite** | Приглашение в tenant: email, role, token_hash, expires_at, invited_user_id, audit. |
| **AuthRefreshToken** | Refresh-токен пользователя. Содержит token_hash, tenant_id, revoked_at/by, payload. |
| **UserAuditLog** | Журнал действий над пользователями (кто, что сделал, когда). |
| **Role** | Определяет уровень доступа (administrator, supervisor, recruiter, viewer). |
| **Tenant** | Определяет границу данных; каждая запись пользователя связана с tenant_id. |
| **JWT Service** | Генерирует и проверяет токены доступа и обновления. |
| **Auth Router** | Обрабатывает маршруты входа, выхода, обновления токена. |
| **RBAC Middleware** | Проверяет права и tenant при каждом запросе. |

### Личный кабинет пользователя

См. подробную спецификацию в `docs/specs/modules/user_profile.md`.

- Профиль и предпочтения пользователя хранятся в JSON (`users.extra.profile`, `user_preferences`).
- Эндпоинты `/api/v1/users/me*` дают возможность управлять профилем, UI-предпочтениями, уведомлениями, активными сессиями и паролем.
- Все операции логируются в `user.self_update`, `user.self_password_change`, а также в общую ленту активности.
- Настройки сохраняют привязку к tenant и учитывают RLS.

## Роли и разрешения (RBAC)

В системе определены следующие роли:

- **administrator** — полный доступ ко всем функциям, управление пользователями, аудит, настройка ACL.
- **supervisor** — управляет рекрутёрами, видит их кандидатов, подтверждает или отклоняет заявки на удаление кандидатов.
- **recruiter** — управляет кандидатами и документами в рамках назначенных компаний/вакансий; имеет доступ к пайплайну своих кандидатов, может создавать, редактировать, переводить по этапам и загружать документы; прямое удаление запрещено — только запрос супервайзеру.
- **viewer** — только просмотр данных.

| Роль           | Кандидаты                                                | Вакансии             | Документы                 | Управление пользователями | Аудит и ACL | Запросы на удаление кандидатов | Пайплайн | Просмотр данных |
|----------------|----------------------------------------------------------|----------------------|---------------------------|---------------------------|-------------|-------------------------------|----------|-----------------|
| administrator  | CRUD всех                                                | CRUD всех            | CRUD всех                 | ✅                        | ✅          | ✅                            | ✅        | ✅              |
| supervisor     | CRUD кандидатов рекрутёров, подтверждение/отклонение удаления | CRUD                | CRUD                     | Управляет рекрутёрами    | Просмотр    | Подтверждает/отклоняет       | ✅        | ✅              |
| recruiter      | CRUD кандидатов в рамках компаний/вакансий с доступом; прямой delete запрещён; stage-change только внутри ACL | CRUD связанных (read/write) | CRUD связанных; загрузка разрешена | ❌                        | Ограниченный просмотр своих ACL | Может только запрашивать      | ✅ (только свои кандидаты) | ✅              |
| viewer         | Только просмотр                                          | Только просмотр      | Только просмотр           | ❌                        | ❌          | ❌                            | Просмотр | ✅              |

### Дополнительные разрешения (feature flags)

- `admin.metaLeads` — доступ к разделу «Админка → Лиды», CRUD credential’ов (`meta_lead_credentials`), настройкам `meta_lead_settings`, ручной маршрутизации лидов. Назначается по умолчанию ролям `administrator` и `supervisor`; остальные роли не имеют доступа. Все действия фиксируются в `audit_log`.

## JWT и токены
- Используется **JWT (JSON Web Token)** с полями:
  - `sub` — user_id  
  - `tenant_id` — для RLS  
  - `role` — роль пользователя  
  - `exp` — срок действия  
  - `supervisor_id` — если у пользователя есть назначенный supervisor (например, у recruiter), передаётся supervisor_id  
- Refresh-токен хранится в Redis или таблице `refresh_tokens`.
- Access-токен живёт 1 час; refresh-токен — 14 дней.
- Логаут удаляет refresh-токен из хранилища.

---

## Безопасность
- Пароли хранятся только в виде hash (bcrypt).
- При вводе неверного пароля более 5 раз — временная блокировка пользователя.
- Все запросы через HTTPS.
- Все операции проверяют `tenant_id` на уровне запроса и RLS.
- `Owner` не может удалить сам себя.
- Создание пользователей возможно только внутри текущего tenant.
- При выдаче токенов система сверяет активность пользователя и tenant.

## События
- `user.created` — создаётся новый пользователь (через регистрацию или administrator).
- `user.login` — успешная авторизация.
- `user.logout` — завершение сессии.
- `user.password_reset` — сброс пароля.
- `user.deactivated` — пользователь отключён администратором.
- `user.invited` — создано приглашение.
- `user.role_changed` — изменена роль участника tenant.
- `user.refresh_revoked` — отозваны refresh-токены пользователя.
- `user.invite_accepted` — приглашение принято, учетная запись активирована.
- `token.expired` — срок действия access-токена истёк.
- `user.supervisor_assigned` — рекрутеру назначен supervisor.
- `candidate.delete_requested` — рекрутер запросил удаление кандидата.
- `candidate.delete_approved` — supervisor подтвердил удаление кандидата.
- `candidate.delete_rejected` — supervisor отклонил удаление кандидата.

## Тестирование
- Тесты находятся в `backend/tests/api/test_auth.py`.
- Проверяются сценарии:
  - Успешный логин, refresh и logout.
  - Ошибки при неверных паролях.
  - Доступ к защищённым эндпоинтам с разными ролями.
  - Отсутствие RLS-утечек между tenant’ами.
  - Истечение токена и корректность refresh.
- При каждом запуске тестов создаются seed-пользователи с ролями administrator, supervisor, recruiter, viewer.

## AI Agent Notes
- Этот модуль является критическим для безопасности всей системы.  
- Любое изменение схемы `User` или логики токенов требует пересмотра RLS и core.md.  
- Агент должен использовать refresh-токены и не создавать access-токены вручную.  
- Все операции над пользователями должны быть tenant-aware.  
- Нельзя добавлять новые роли без обновления `rules.md`, `core.md` и `glossary.md`.
