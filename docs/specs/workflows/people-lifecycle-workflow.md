# People Lifecycle Workflow — продуктовое поведение после первого контакта

**Status:** canonical product workflow (L2) — **обязателен перед любой UI-спекой** intake, candidate, HR.  
**Hierarchy:** L2 workflow canon.  
**Owner:** Product + Recruitment + HR.

**Назначение:** зафиксировать **что видит и что может делать пользователь** на каждом жизненном этапе человека в HostFlow — после того, как настройка системы завершена ([consumer-setup-flow-people-to-employee.md](consumer-setup-flow-people-to-employee.md)). ## 0. Два фундаментальных UX-принципа

### 0.1 Continuity данных на границах жизненного цикла

> **При handoff между этапами данные и артефакты не теряются — документы, активности, audit.**

Архитектурно на границах появляются новые записи (`Lead` → `Candidate` → `WorkforceEmployee`, …). **Платформа** сохраняет непрерывность для передачи в HR и audit:

| Переход | Что сохраняется в системе |
|---------|---------------------------|
| Входящий контакт → Кандидат | Контакты, источник, переписка, звонки, RODO-аудит |
| Кандидат → Сотрудник | Те же файлы, закрытые требования, read-only история |
| Сотрудник → Активный сотрудник | HR-данные, операционные документы |

**Запрещено в продукте (data continuity):**

- «Пропал» входящий контакт без ссылки на кандидата после convert.
- Дублирующий «позвонить впервые» на кандидате, если звонок уже был на lead.
- Новый набор документов у HR вместо файлов из рекрутинга.

**Не путать с единым экраном для всех ролей.** Рекрутер работает в Recruitment, HR — в HR. Им **не нужно** «не замечать смену модуля» — они **не открывают** чужой модуль. Им нужен **один продуктовый паттерн** внутри своего модуля (см. ADR-017 §0).

### 0.2 Единый продуктовый паттерн работы с записью

> **В любом модуле оператор понимает: где он, что сделано, что мешает, что делать дальше.**

Паттерн: **информация → требования → состояние → действия** (blockers + next action).

Lead Workspace, Candidate Card, HR Dossier, Fleet driver card — **разные экраны**, **один язык**. Детали по этапам — в частях 1–4 ниже; техническая реализация — [ADR-017](../architecture/ADR-017-workspace-layer.md).

### 0.3 Workspace Layer — как реализуется паттерн

**Workspace** — имя **паттерна и платформенной capability**, не отдельный экран «для всех» ([ADR-017](../architecture/ADR-017-workspace-layer.md)).

Модуль **публикует** declarations (разделы, readiness, next action). Платформа **композирует** их на экране записи модуля. Зависимость **односторонняя:** Module → Workspace contracts.

Логические зоны (на любом экране модуля):

```text
┌──────────────┬────────────────────────────┬──────────────────┐
│  Навигация   │   Рабочая область          │  Status          │
│  (sections)  │   информация / требования  │  blockers        │
│              │                            │  next action     │
└──────────────┴────────────────────────────┴──────────────────┘
```

**Status** агрегирует Readiness **видимых** модулей для этой роли. Next action решает модуль; платформа **только показывает** приоритетное.

Оператор не ищет «где кнопка» — blockers и CTA **в одном месте на экране**, в любом модуле.

## 1. Обзор жизненного цикла (продуктовый)

```text
[1] Входящий контакт     — intake / оценка / решение
         ↓ convert
[2] Кандидат             — требования / документы / готовность
         ↓ handoff
[3] Сотрудник (HR)       — верификация / подтверждение
         ↓ approve
[4] Активный сотрудник   — employment lifecycle (контракт, сроки, задачи)
```

Платформенная цепочка (для разработчиков): `Lead → Candidate → RecruitmentApplication → CandidateHandoff → WorkforceEmployee → Employment Lifecycle`.

## Часть 1. Входящий контакт (Lead Workspace)

**UI-название этапа:** «Входящий контакт» или «Новый контакт».  
**Платформа:** `Lead`.  
**Вопрос этапа:** *Подходит ли этот человек — и что с ним делать?*

### 1.1 Что видит пользователь

| Блок | Содержание |
|------|------------|
| **Кто пришёл** | Имя, телефон, email, язык, гражданство — из источника |
| **Откуда** | Источник (Meta Form, Landing, WhatsApp, …), кампания, дата |
| **Куда направлен** | Вакансия (подсказка или подтверждённая), воронка, требования, ответственный |
| **Краткая оценка** | Опыт, категория, документы (если есть), fit в одну строку / badge |
| **RODO / согласие** | Статус: отправлено / покрыто источником / требуется действие |
| **История контактов** | Звонки, сообщения, заметки — компактная лента |
| **Дубликат** | Предупреждение, если похож на существующего кандидата / сотрудника |

**Не доминируют на этом этапе:** воронка кандидата, тяжёлый dossier, checklist документов водителя, HR-поля, automation config.

### 1.2 Что можно сделать

| Действие | Смысл |
|----------|--------|
| **Позвонить / написать** | Зафиксировать контакт (Activity, не смена статуса) |
| **Отправить RODO** | Art. 14, если не покрыто источником |
| **Отметить «согласие на источнике»** | Meta / форма HostFlow уже получили согласие |
| **Подтвердить вакансию** | Зафиксировать канонический маршрут (suggest → select → confirm) |
| **Квалифицировать** | Принять для следующего шага |
| **Отклонить** | Закрыть с причиной (taxonomy: опыт, гражданство, язык, …) |
| **В пул** | Сохранить без конкретной вакансии |
| **Запросить информацию** | Нужны данные / документы до решения |
| **Проверить дубликат** | Сравнить с существующим досье |
| **Перевести в кандидата** | Положительное intake-решение → создание кандидата |

При **первом неизвестном источнике** (маршрут не настроен):

| Действие | Смысл |
|----------|--------|
| **Указать маршрут** | Вакансия + воронка + требования + ответственный |
| **☑ Запомнить** | Создать routing rule → автопилот для следующих |

### 1.3 Почему нельзя перевести дальше (блокеры)

Правая колонка показывает **конкретный блокер** и **одно рекомендуемое действие**:

| Блокер | Сообщение пользователю (пример) | Разблокировка |
|--------|--------------------------------|---------------|
| RODO не закрыт | «Отправьте уведомление RODO или отметьте согласие на источнике» | Send RODO / source-provided |
| Вакансия не подтверждена | «Подтвердите вакансию для этого контакта» | Confirm vacancy |
| Дубликат не разрешён | «Примите решение по дубликату» | Duplicate review |
| Отклонён | «Контакт закрыт: [причина]» | — (терминальное состояние) |
| Запрошена информация | «Дождитесь ответа или обновите данные» | Получить данные / снять блок |
| Неизвестный источник | «Укажите, куда направлять людей из этого источника» | Маршрут + «Запомнить» |
| В пуле без вакансии | «Для перевода в кандидата на вакансию — выберите вакансию» | Выбор вакансии (pool path — отдельный) |

**Семантика:** блокер — не «ошибка системы», а **следующий шаг intake-решения**.

### 1.4 Критерий завершения этапа

Этап завершён, когда принято одно из **терминальных intake-решений**:

- **Переведён в кандидата** (положительный путь);
- **Отклонён** (с причиной);
- **В пуле** (intent сохранён, вакансия опциональна);
- **Привязан к существующему досье** (дубликат — тот же человек).

После convert пользователь **переходит в Candidate Workspace** того же человека — с сохранённым контекстом (§0.1).

### 1.5 Статус реализации

| Поведение | Статус |
|-----------|--------|
| Intake actions (qualify/reject/pool/…) | ✅ Backend + UI (Slice 2) |
| RODO gates | ✅ |
| Vacancy confirm | ✅ |
| Qualification summary (compact) | ✅ (Slice 3) |
| Activity continuity (no fake first call) | 🔄 Slice 4 — guards в работе |
| Lead Workspace layout (3-column shell) | 🔄 частично; целевой — этот документ |

## Часть 2. Кандидат (Candidate Workspace)

**UI-название:** «Кандидат».  
**Платформа:** `Candidate` + `RecruitmentApplication`.  
**Вопрос этапа:** *Выполнены ли все требования — и можно ли передавать в HR?*

### 2.1 Разделы Workspace

| Раздел (навигация слева) | Назначение | Приоритет |
|--------------------------|------------|-----------|
| **Overview** | Сводка, стадия, быстрый контекст | Entry |
| **Требования** | Checklist-first: что закрыть | **Primary** — главная рабочая область |
| **Профиль** | Контакты, персональные данные, вакансия | Контекст |
| **Документы** | Файлы в Document Hub, привязанные к требованиям | Через требования или отдельный просмотр |
| **Заявки** | На какие вакансии / циклы претендует | Intent layer |
| **Коммуникации** | Переписка, звонки | Continuity с Lead |
| **История / Timeline** | Timeline: стадии, решения, активности | Read-heavy |
| **Activity** | Операционные действия | Continuity |
| **Происхождение** | Ссылка на входящий контакт (откуда пришёл) | Audit / support |

**Operator path (ADR-017):** **Candidate Card** на `/app/candidates/:id` — это и есть workspace. Step 6 не создаёт новый экран, а **рефакторит карточку**: единый status rail, section providers из registry, Requirements в рабочей области карточки.

**A3 spike (2026-07-01):** `/app/candidates/:id/requirements` доказал capability renderer. **Не** целевой UX — дублирует rail карточки. После Step 6 маршрут **retire** → section внутри той же карточки.

**Status rail (справа):** один на карточке — blockers, next action, readiness. Клик по блоку «Требования» переключает section in-place. CTA **не** «Открыть workspace».

### 2.2 Документы и требования

Пользователь **не** составляет список документов вручную. Система показывает **требования** (UI: из «Профиля требований» / Entity Profile):

| Тип требования | Пример | Как закрывается |
|----------------|--------|-----------------|
| Данные | Контакты, адрес, PESEL | Заполнение полей |
| Документ | Паспорт, права CE, Code 95 | Файл + approve |
| Документ + данные | Виза, karta pobytu | Файл + извлечённые поля + approve |
| Операционное | Позвонить, запросить документ | Activity с исходом |

Для каждого требования пользователь видит:

- статус: не начато / в работе / на проверке / закрыто / не применимо;
- **чем подтверждается** (варианты evidence);
- связанные документы;
- причину блокировки, если не закрыто.

### 2.3 Что показывает Readiness (правая колонка)

**Readiness** — не «стадия воронки», а **доказательство готовности**:

| Показатель | Смысл для пользователя |
|------------|------------------------|
| **Прогресс требований** | «7 из 12 закрыто» |
| **Блокеры** | Список того, что мешает (с ссылкой на требование) |
| **Готовность к передаче** | Зелёный / жёлтый / красный — transfer-readiness |
| **Следующий шаг** | Одно рекомендуемое действие: «Загрузите паспорт», «Подтвердите Code 95», … |
| **Стадия воронки** | Вторично; смена стадии **блокируется**, если требования не закрыты |

Переход стадии вперёд без закрытых blocking requirements → система объясняет **почему**, не молчаливый 409.

### 2.4 Когда появляется Handoff

**Handoff** (передача в HR) становится доступен, когда:

1. Все **blocking requirements** в статусе `satisfied` или `not_applicable`;
2. **Transfer-readiness** зелёный (Requirement Engine + transfer policy);
3. Стадия в зоне handoff (`ready_for_handoff` / `ready_for_hr` — по настройке воронки);
4. Нет незакрытых блокеров duplicate / identity.

**Правая колонка при готовности:**

> «Кандидат готов к передаче в HR. [Передать]»

**До готовности** кнопка Handoff **не показывается** или disabled с объяснением — не «серую кнопку без текста».

### 2.5 Что можно сделать

| Действие | Когда |
|----------|-------|
| Закрыть требование | Основная работа рекрутёра |
| Загрузить / привязать документ | В контексте требования |
| Одобрить / отклонить evidence | Recruitment approve |
| Позвонить / написать | Операционные требования |
| Сменить стадию воронки | Если gates позволяют |
| **Передать в HR** | Readiness зелёный |
| Вернуть в пул / отклонить | Продуктовые exit paths |

### 2.6 Переход в Employee Workspace

При **Передать в HR**:

- создаётся запрос handoff (`CandidateHandoff`);
- HR видит задачу на приём;
- рекрутёр остаётся в Candidate Workspace (read-only зона растёт после accept);
- пользователь видит **ссылку «Открыть в HR»** на того же человека — не «нового сотрудника из ниоткуда».

### 2.7 Статус реализации

| Поведение | Статус |
|-----------|--------|
| Requirements API + evidence workflow | ✅ Backend |
| Requirements Workspace route | 🔄 A3 backlog |
| Transfer-readiness gates | ✅ Backend |
| Handoff → WorkforceEmployee | ✅ (accept path) |
| Continuity Lead → Candidate activities | 🔄 Slice 4 |

## Часть 3. Сотрудник — HR-приём (Employee Workspace)

**UI-название:** «Сотрудник» (этап верификации / оформления).  
**Платформа:** `WorkforceEmployee` + `WorkforceHrCase`.  
**Вопрос этапа:** *Подтверждены ли данные и документы — можно ли оформить?*

### 3.1 Что перенеслось из рекрутинга

| Артефакт | Поведение |
|----------|-----------|
| **Документы** | **Те же файлы** в Document Hub — через `document_entity_links`, без копирования |
| **Закрытые требования** | Снимок `requirement_fulfillments[]` — что рекрутинг подтвердил |
| **Персональные данные** | Снимок кандидата (`candidate_snapshot`) |
| **RODO-аудит** | Read-only в контексте (`rodo_lead_audit`) |
| **История контактов** | Read-only / linked — не дублируется |
| **Ссылка на кандидата** | «Открыть recruitment dossier» |

Пользователь HR **не загружает заново** то, что рекрутинг уже собрал — он **проверяет**.

### 3.2 Что проверяется повторно

HR проходит **те же логические блоки**, что recruitment package (симметрия dossier):

| Блок | Что делает HR |
|------|---------------|
| Документ (паспорт, legal stay, права, …) | Просмотр файла + полей → **Подтвердить данные** |
| Только данные (контакты, адрес) | Проверка полей → подтверждение |
| Опциональный файл (опыт работы) | Поля, файл опционален |

Каждый блок: поля, действия с файлом, кнопка **Confirm data**. Все блоки подтверждены → CTA **Next step** (eligibility / employment decision).

### 3.3 Что уже нельзя менять

| Зона | Правило |
|------|---------|
| **Recruitment dossier** | Read-only для рекрутёра после materialization (`processing_by_hr`) |
| **Recruitment approve на evidence** | Закрыт — HR свой review context |
| **Стадия «нанят»** | Рекрутёр не ставит `hired` при включённом handoff lane |
| **Повторный handoff** | Идемпотентно — один сотрудник на кандидата |

Пользователь HR видит, **что пришло из рекрутинга**, и отдельно — **что он подтверждает**.

### 3.4 Что подтверждает HR

| Решение | Смысл |
|---------|--------|
| **Подтвердить блок** | Данные/документ верны для HR |
| **Запросить исправления** | Вернуть в рекрутинг с комментарием |
| **Отклонить** | Не проходит HR-проверку |
| **Одобрить трудоустройство** | Employment decision → переход в Active Employee |

### 3.5 Разделы Employee Workspace (HR-приём)

| Раздел | Назначение |
|--------|------------|
| **Верификация** | Primary — блоки dossier |
| **Документы** | Hub view с HR review context |
| **Контекст рекрутинга** | Read-only: откуда пришёл, что закрыто |
| **Решение** | Eligibility, approve / return / reject |
| **Задачи после одобрения** | Onboarding tasks (collapsed до approve) |

### 3.6 Статус реализации

| Поведение | Статус |
|-----------|--------|
| Employee dossier verification | ✅ Implemented |
| Document links (no copy) | ✅ |
| Return to recruitment | ✅ |
| Recruitment read-only lock | ✅ Enforced |

## Часть 4. Активный сотрудник (Active Employee Workspace)

**UI-название:** «Сотрудник» (в работе).  
**Платформа:** Employment Lifecycle *(архитектурно зарезервировано)*.  
**Вопрос этапа:** *Что нужно поддерживать, пока человек работает?*

> Этот блок **продуктово зафиксирован**, детальная реализация — отдельные эпики. UI не проектируется до стабилизации Частей 1–3.

### 4.1 Что происходит дальше

После **одобрения трудоустройства** HR:

- сотрудник переходит в **операционный** режим (не приём, а сопровождение);
- ownership полностью у **HR / Workforce**;
- recruitment dossier остаётся **архивом** (read-only, ссылка для аудита).

### 4.2 Какие документы становятся операционными

| Категория | Примеры | Поведение |
|-----------|---------|-----------|
| **Срок действия** | Права, медкомиссия, виза, karta pobytu | Напоминания до истечения |
| **Трудовые** | Контракт, доп. соглашения | HR-only документы в Hub |
| **Compliance** | ZUS, разрешения на работу | Чеклисты HR |
| **Связь с Fleet** *(будущее)* | Tachograph, назначение на ТС | Отдельный модуль |

Документы рекрутинга **не дублируются** — operational layer добавляет **review context** и **expiry monitoring**.

### 4.3 Какие задачи появляются

| Тип задачи | Пример |
|------------|--------|
| Onboarding | Оформление, первый рабочий день |
| Продление документа | «Права истекают через 30 дней» |
| Изменение условий | Контракт, должность, перевод |
| Offboarding *(зарезервировано)* | Увольнение, закрытие кейса |
| Rehire *(зарезервировано)* | Возврат бывшего сотрудника — новый цикл |

### 4.4 Разделы Active Employee Workspace (целевые)

| Раздел | Назначение |
|--------|------------|
| **Обзор** | Статус employment, должность, подразделение |
| **Документы** | Операционные + сроки |
| **Контракт и условия** | Employment terms |
| **Задачи** | HR operational tasks |
| **История** | Кадровые события |

### 4.5 Связь с другими модулями (границы)

| Модуль | Связь |
|--------|-------|
| **Fleet** | Назначение на транспорт — после стабильного Employee |
| **Payroll / Finance** | События биллинга — отдельный контур |
| **Services** | B2B-услуги — не смешивать с employment |

## 5. Непрерывность между Workspace (сквозные правила)

### 5.1 Навигация «тот же человек»

На каждом Workspace в шапке:

```text
Иван Петров · +48 500 123 456
Входящий контакт → Кандидат → Сотрудник        [текущий этап выделен]
```

Клик по прошлому этапу — read-only или контекстный переход, не потеря текущей работы.

### 5.2 Что переносится автоматически

| Откуда → Куда | Перенос |
|---------------|---------|
| Lead → Candidate | Activities, notes, call outcomes, confirmed vacancy, RODO audit, source |
| Candidate → Employee | Documents (links), fulfillments, snapshot, communications (read) |
| Employee (HR) → Active | Verified fields, HR confirmations, employment decision |

### 5.3 Что не переносится (намеренно)

| Не переносить | Почему |
|---------------|--------|
| Intake-only статусы | Другой жизненный этап |
| Открытые intake blockers | Уже resolved на convert |
| Fake tasks (дубль «позвонить») | Activity continuity guards |
| Recruitment stage как HR stage | Разные воронки |

## 7. Product gates (перед UI-спеками)

Любая UI-спека intake, candidate или HR **должна отвечать**:

1. **[ADR-017](../architecture/ADR-017-workspace-layer.md) §0** — единый паттерн: информация → требования → состояние → действия; модуль не рисует чужой layout.
2. **Status zone** — blockers + next action в предсказуемом месте на экране записи (не дублировать на отдельных страницах)?
3. **Data continuity** — документы/активности не теряются на handoff (не «единый экран для всех ролей»)?
4. **Поведение до пикселей** — этот документ описывает действие; UI только следует?
5. **Readiness ≠ stage** — готовность из требований, не из названия стадии?
6. **Handoff gated** — кнопка только при зелёном transfer-readiness?
7. **HR = verify, not re-upload** — те же документы, новый review context?

**Порядок работ:**

```text
consumer-setup-flow (настройка)
  → people-lifecycle-workflow (поведение)
  → hostflow-interaction-architecture (слои List/Workspace/Capabilities/Domain)
  → ADR-017 (контракты declarations + readiness)
  → UI-спеки section renderers
```
