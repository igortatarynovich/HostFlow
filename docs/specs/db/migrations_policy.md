# 🔄 Database Migrations & Versioning Policy

> Политика для Alembic миграций, управления версиями API и данных.

---

## 1. Общие принципы
- Миграции **только вперёд**. Откат возможен только в dev-среде.
- Каждая миграция имеет уникальный идентификатор в формате `YYYYMMDDHHMM_<slug>`.
- Все миграции исполняются через `make mig` или `alembic upgrade head` (в контейнере).
- Структура миграций хранится в `backend/alembic/versions`.
- Команда `alembic upgrade head` должна применяться без конфликтов голов (используем `alembic merge` при расхождении веток).

---

## 2. Процедура подготовки

1. Обновить модели и схемы (`backend/app/models`, `docs/specs/db/*.md`).
2. Сгенерировать миграцию: `make mig-rev MSG="describe change"`.
3. Провести ручную ревизию (`upgrade`/`downgrade`), убедиться в идемпотентности `upgrade`.
4. Обновить сиды, если логика требует (см. `backend/app/db/seeds`).
5. Запустить `make mig && make test`.

> Для breaking-изменений обязательно приложить инструкцию по данным (скрипт или cron).

---

## 3. Типы релизов

| Тип релиза | Совместимость API | Требования |
|------------|-------------------|------------|
| `patch` | назад совместим | Фиксы, без миграций |
| `minor` | назад совместим | Новые поля/таблицы (только additive миграции) |
| `major` | возможны breaking changes | Требуется миграция данных и обновление справочников |

- При `major` релизе добавляем стори в `docs/specs/roadmap.md` и составляем план миграции.
- Если API ломается, необходимо версионировать endpoint (`/api/v2/...`) или добавить флаг совместимости.

---

## 4. Rollout

- Применяем миграции сначала в staging (CI), затем в production.
- Для критичных миграций (долгие операции) использовать `--sql` и готовить скрипт (`alembic upgrade head --sql > migrate.sql`).
- В продакшне миграции запускаются через `docker compose exec backend alembic upgrade head`.
- В случае отказа миграции → фиксируем причину, создаём исправление, новая миграция **не** заменяет старую, а следует поверх.

---

## 5. Тестирование

- Pytest с флагом `--migrations` поднимает чистую БД, применяет миграции и запускает тесты.
- Smoke-тест в CI проверяет, что `alembic downgrade -1` работает (только для dev).
- Сид-данные должны соответствовать актуальной схеме (проверяются в `make seed`).

---

## 6. Документация

- Обновлять связанные файлы в `docs/specs/db/*.md` при каждой миграции.
- Добавлять запись в changelog (`docs/specs/db/migrations_plan_<module>.md`) при крупных изменениях.
- Для модулей с API фиксировать изменения в соответствующих спецификах (например, `modules/documents.md`).
