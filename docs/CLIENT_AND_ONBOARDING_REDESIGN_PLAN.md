# Оценка логики и план: онбординг + тип компании + клиенты (Citronex / POLTRAK)

## 1. Оценка описанной логики

### 1.1 Что вы описали (кратко)

- **После регистрации** держатель лицензии **обязательно создаёт компанию**. У компании один тип из подсписка: **агентство** или **прямой работодатель**.
- После создания компании можно создавать клиентов, рекламу, работать с CRM.
- **Агентство** (вы): компания типа «агентство» → будут клиенты, для которых обрабатываете кандидатов.
  - **Клиент 1 — Citronex**: купил лицензию, есть свой тенант и компания типа «работодатель». При создании клиента «Citronex» в своём тенанте система находит такую компанию и предлагает привязать профиль клиента к ней. Настройки: видеть вакансии, созданные для этого клиента, и урезанные профили кандидатов; после передачи — полный профиль.
  - **Клиент 2 — POLTRAK**: лицензии нет, своего тенанта нет. Система не находит «такого клиента в базе». Доступ только через уникальную ссылку на портал клиента для просмотра переданных кандидатов.
- Итог: однозначно понятно, что какому тенанту принадлежит и что кому показывать.

### 1.2 Оценка

Логика **последовательная и пригодна для реализации**. Она хорошо совпадает с уже описанной в `client_and_subscription_model.md` и `multi_tenant_model.md`:

- Разделение «клиент с тенантом» (Citronex) и «клиент без тенанта» (POLTRAK) уже заложено в модели (`TenantLink.client_tenant_id` vs `client_company_id`, компания внутри тенанта агентства).
- Обязательное «сначала компания, потом всё остальное» упрощает онбординг и даёт один чёткий тип контекста (агентство или работодатель).
- Привязка профиля клиента к существующей компании (поиск «есть такая компания в системе») и портал по ссылке для клиентов без лицензии — естественные расширения текущей модели.

## 2. Уточнения и предложения по доработке

### 2.1 Где хранить тип: тенант или компания

Сейчас в коде:

- **Тип есть у тенанта**: `Tenant.type` = `agency` | `company` | `platform`.
- **У компании типа нет** (есть только `tenant_id`, название и т.д.).

Вы говорите: «компания с типом агентство или работодатель». Возможны два варианта:

- **Вариант A (рекомендуемый):** тип остаётся у **тенанта**. Онбординг: «создать компанию» по сути означает «создать тенант + первую компанию», при этом пользователь выбирает тип компании (агентство / работодатель), и мы выставляем `Tenant.type` = `agency` или `company`. В UI везде формулировка «тип компании» (агентство / работодатель), в БД — по-прежнему `Tenant.type`. Один тенант = одна «роль» (агентство или работодатель).
- **Вариант B:** ввести отдельно `Company.type` (agency / employer). Тогда в одном тенанте теоретически могут быть компании разных типов; сложнее правила и сценарии. Не рекомендуется, если не нужна явно «несколько типов компаний в одном тенанте».

Рекомендация: **вариант A** — не добавлять тип компании в БД, а в онбординге и UI трактовать выбор пользователя как тип компании и записывать его в `Tenant.type`.

### 2.2 «Один тип компании в подсписке»

Имеется в виду: при создании первой компании пользователь выбирает **один** тип из списка (агентство / работодатель), и дальше с этим типом живёт весь тенант. Это совпадает с вариантом A выше и с текущей моделью (один тенант — один тип). Дополнительно можно:

- при смене типа тенанта (если такое когда-то понадобится) проверять, что нет противоречащих данных (например, уже созданных «клиентов» при смене с agency на company);
- в UI явно показывать: «Ваш рабочий профиль: агентство» или «прямой работодатель».

### 2.3 Создание клиента Citronex: привязка к существующей компании

- Агентство создаёт «клиента» в своём тенанте.
- Система ищет в платформе компанию (и/или тенант), которую можно трактовать как этого клиента — по названию, домену, email и т.д. (критерии поиска нужно зафиксировать).
- Если найдена компания в **другом тенанте** с типом «работодатель» (tenant.type = company) → предлагаем привязать профиль клиента к ней: создаём/обновляем `TenantLink` с `client_tenant_id` = тот тенант, при необходимости `handoff_include_company_id` = компания из того тенанта (или из агентства — по бизнес-правилу).
- Настройки «видеть вакансии» / «видеть урезанные профили» уже частично есть (handoff, маска PII); их нужно явно вынести в настройки связи (например в `TenantLink.features_json` или отдельные флаги).

Улучшение: на экране создания/редактирования клиента показывать блок «В системе найдена компания Citronex (работодатель). Привязать к этому клиенту?» с кнопкой «Привязать» и последующей настройкой прав (вакансии, урезанные профили, handoff).

### 2.4 Создание клиента POLTRAK (без лицензии)

- Своего тенанта нет → поиск «есть ли такой клиент в системе» ничего не находит (или находит только компании внутри тенанта агентства).
- Агентство создаёт «профиль клиента»: по сути это **компания в тенанте агентства** (например «POLTRAK») + запись в **TenantLink** с `client_company_id` = эта компания, `client_tenant_id` = NULL.
- Доступ: только по **уникальной ссылке портала клиента** (токен/ссылку храним в БД, привязанную к `TenantLink` или к компании). По ссылке пользователь попадает в «портал клиента» без полноценного логина в тенант и видит только переданных кандидатов (handoff в эту компанию).

Так и задумано в текущей архитектуре: клиент без тенанта = company под агентством + `client_company_id` в TenantLink; портал по ссылке — отдельная фича (отдельная точка входа, возможно без пароля или с одноразовым токеном).

### 2.5 Вакансии «для клиента»

Вы пишете: «вакансии, которые создаю для этого клиента». Нужно однозначно решить:

- Вакансии создаются в тенанте **агентства** и привязываются к **компании** (в тенанте агентства или, для Citronex, к компании, привязанной через tenant_links). Тогда «вакансии для Citronex» = вакансии компании, которая в tenant_links как handoff_include_company_id для client_tenant_id = Citronex (или вакансии компании Citronex в их тенанте — в зависимости от того, где вы их создаёте).
- Чтобы «кандидаты двух вакансий» стабильно показывались у Citronex, в `tenant_links` для Citronex должны быть привязки **всех** компаний (агентства), у которых есть эти вакансии (handoff_include_company_id). Это уже описано в миграциях и спеках; в плане ниже — проверка и при необходимости исправление scope/RLS.

## 3. План реализации

### Фаза 0. Срочно: список кандидатов для Citronex (две вакансии)

**Цель:** клиент с тенантом (Citronex) видит всех кандидатов по вакансиям привязанных компаний, а не только по handoff.

- Уже сделано в коде: scope = handoff ИЛИ кандидаты по привязанным вакансиям/компаниям; RLS выставляется по scope_tenant.
- Остаётся проверить на стенде:
  - В `tenant_links` для Citronex есть строки с `client_tenant_id` = тенант Citronex и `handoff_include_company_id` = компании, у которых есть нужные две вакансии.
  - Запрос списка уходит с `scope_tenant_id` = Citronex и заголовком `X-Tenant-Id` = Citronex (или бэкенд выставляет `app.tenant_id` по scope_tenant).
- При необходимости: скрипт/миграция, которая по тенанту Citronex и списку компаний агентства с вакансиями дополняет `tenant_links` недостающими связями.

### Фаза 1. Онбординг: «сначала компания»

**Цель:** после регистрации пользователь не может полноценно пользоваться системой, пока не создаст компанию; при создании выбирает тип (агентство / работодатель).

1. **Бэкенд**
   - После регистрации/логина проверять: у тенанта есть ли хотя бы одна компания (или явный флаг «онбординг пройден»). Если нет — API возвращает признак «требуется создание компании» (например `onboarding_required: true` или 403 с кодом).
   - Эндпоинт создания первой компании (или общий создание компании) принимает параметр **тип компании** (agency / employer). В зависимости от выбора выставлять `Tenant.type` = `agency` или `company` (если ещё не задан). Для существующих тенантов при необходимости разрешить только если тип не конфликтует.
   - Опционально: отдельная сущность «онбординг» (шаг: company_created) для явного учёта прогресса.

2. **Фронт**
   - После логина при `onboarding_required` редирект на шаг «Создайте компанию» (один экран).
   - Форма: название компании, тип — выбор из подсписка: **Агентство** / **Прямой работодатель** (соответственно Tenant.type = agency | company).
   - После успешного создания — редирект в основное приложение (дашборд/кандидаты и т.д.), онбординг считается пройденным.

3. **Миграции**
   - При необходимости: дефолт `Tenant.type` для существующих тенантов (например agency), чтобы старые данные не сломались.

### Фаза 2. Клиенты агентства: создание и привязка

**Цель:** агентство создаёт «клиента»; для клиентов с тенантом в системе — привязка к существующей компании/тенанту; настройки видимости вакансий и урезанных профилей.

1. **Модель и API**
   - «Клиент» для агентства = запись в **TenantLink** (agency_tenant_id = агентство, client_tenant_id или client_company_id) + при необходимости «профиль» (название, контакты) — хранить в TenantLink или в связанной Company.
   - Эндпоинты (примерно):
     - `POST /tenant-links` (или `/clients`) — создание клиента: тело содержит название, опционально поиск «привязать к существующей компании» (по имени/домену). Бэкенд при наличии совпадения с компанией в другом тенанте (type=company) возвращает кандидата на привязку или сразу создаёт связь с `client_tenant_id` и при необходимости `handoff_include_company_id`.
     - `GET /tenant-links` — список клиентов агентства (с полями: имя, привязан к тенанту/компании, handoff_enabled, видеть вакансии, видеть урезанные профили).
     - `PATCH /tenant-links/{id}` — обновление настроек (в т.ч. «видеть вакансии», «видеть урезанные профили», handoff_enabled).

2. **Поиск «есть такая компания в системе»**
   - При создании клиента (по имени или домену) поиск:
     - компании с таким именем/доменом в **других** тенантах, где `Tenant.type = company` (работодатели).
   - Результат: «Найдена компания X в системе (работодатель). Привязать?» → при подтверждении создаётся TenantLink с `client_tenant_id` = тенант этой компании, при необходимости заполняется `handoff_include_company_id` (компания из тенанта клиента или из агентства — по правилу, кого считаем «вакансиями клиента»).

3. **Фронт**
   - Раздел «Клиенты» (или внутри «Настройки» / «Компании»): список клиентов (tenant_links), кнопка «Добавить клиента».
   - Форма добавления: название, опционально поиск компании; при наличии совпадения — блок «Привязать к компании X» и настройки (вакансии, урезанные профили, handoff).
   - Редактирование клиента: те же настройки + при необходимости смена привязки.

### Фаза 3. Портал клиента по ссылке (клиенты без тенанта, POLTRAK)

**Цель:** клиент без лицензии (нет своего тенанта) получает доступ только по уникальной ссылке и видит только переданных ему кандидатов.

1. **Бэкенд**
   - Сущность «ссылка портала клиента»: привязка к TenantLink (или к client_company_id), уникальный токен (UUID или длинный случайный строки), опционально срок действия, опционально пароль/пин.
   - Эндпоинты:
     - `POST /tenant-links/{id}/portal-link` — сгенерировать/обновить ссылку (возвращает URL и токен).
     - `GET /public/client-portal?token=...` — вход на портал по токену (установка сессии/куки только для чтения переданных кандидатов).
   - Авторизация по токену: определить tenant_link (и client_company_id); scope кандидатов = только с handoff в эту компанию/тенант; только чтение, без доступа к остальному CRM.

2. **Фронт**
   - Публичная страница портала клиента: по токену показывается список переданных кандидатов (и при необходимости карточка без редактирования). Без меню агентства и без смены тенанта.
   - В разделе «Клиенты» у клиента без тенанта (только client_company_id): блок «Доступ по ссылке» — «Создать ссылку», «Скопировать ссылку», «Отозвать».

### Фаза 4. Согласование scope и RLS с новой моделью

- После внедрения «клиент = TenantLink» и портала по ссылке:
  - Проверить, что список кандидатов для тенанта Citronex строится по tenant_links (client_tenant_id + handoff_include_company_id) и что RLS не режет строки (app.tenant_id выставляется по scope).
  - Для входа по ссылке портала: отдельный scope «только handoff в эту company» без использования tenant_id клиента (его нет).
- Документировать в `client_and_subscription_model.md` и в коде правила: кто что видит при наличии/отсутствии тенанта и при доступе по ссылке.

## 5. Итог

- Описанная вами логика **корректна и реализуема**; она уточняет и упорядочивает текущую модель (клиент с/без тенанта, привязка к компании, портал по ссылке).
- Рекомендуемые доработки: тип оставить на уровне тенанта и трактовать в онбординге как «тип компании» (вариант A); явный экран привязки клиента к найденной компании; отдельная сущность «ссылка портала» для клиентов без тенанта.
- План разбит на фазы 0–4; фаза 0 решает текущую боль с «двумя вакансиями», фазы 1–3 вводят онбординг, клиентов и портал по ссылке, фаза 4 фиксирует правила видимости и документирует их.
