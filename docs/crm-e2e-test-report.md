# End-to-End тестирование CRM (Customer Journey + Product Flow)

> Важно: основной рабочий документ готовности к запуску продаж теперь ведется в `docs/crm-production-readiness-ssot.md` (Single Source of Truth).  
> Этот файл сохраняется как исторический E2E-аудит и источник контекста.

Дата: 2026-03-11  
Формат: продуктовый E2E-аудит на основе текущей реализации frontend/backend (`hostflow-frontend`, `backend`)  
Ограничение: Stripe не подключен, платежный этап симулирован.

## 1) User Journey Map (Landing → Payment → Onboarding → First Value)

### A. Текущий фактический путь в продукте
1. Пользователь попадает на публичные страницы `/public/*` или `/login`.
2. На публичных страницах основной CTA ведет в candidate intake (`/public/intake`), а не в покупку CRM.
3. Вход в CRM возможен через:
4. Логин существующего пользователя (`/api/v1/auth/login`).
5. Принятие приглашения (`/invite/accept` -> `/api/v1/auth/invite/accept`).
6. Self-signup (новый аккаунт без приглашения) отсутствует.
7. После входа: если нет компании, принудительный редирект на `/app/onboarding/company`.
8. Onboarding = создание компании (название + тип: agency/employer).
9. Дальше пользователь попадает в рабочее пространство (`/app/overview`).
10. Первый value обычно достигается через:
11. Добавление компании/кандидатов/лидов.
12. Настройку команды и прав в `Settings -> Users`.
13. В коммуникациях: настройку каналов и очередей.

### B. Целевой путь для SaaS CRM (рекомендованный)
1. Landing с явным позиционированием CRM + 3 тарифа + CTA `Start free trial`.
2. Выбор тарифа (Starter/Team/Pro) с прозрачными лимитами.
3. Регистрация аккаунта (email+password) до оплаты.
4. Создание workspace (имя + тип бизнеса) в 1 шаг.
5. Stripe Checkout.
6. Возврат в приложение на `payment/success`.
7. Авто-активация подписки + запуск onboarding-чеклиста.
8. First value за <5 минут: создать первого клиента/лида и зафиксировать следующий шаг (task/note/status).

## 2) Список всех сценариев

### 2.1 Acquisition / Entry
- S1: Пользователь с публичной страницы понимает ценность CRM и идет в trial.
- S2: Пользователь попадает на login напрямую и может создать новый аккаунт.
- S3: Пользователь приходит по invite-ссылке и активирует аккаунт.

### 2.2 Pricing / Subscriptions
- S4: Просмотр тарифов Starter/Team/Pro.
- S5: Сравнение лимитов по пользователям/фичам.
- S6: Выбор тарифа и переход к оплате.
- S7: Апгрейд тарифа.
- S8: Даунгрейд тарифа.
- S9: Отмена подписки.

### 2.3 Registration
- S10: Регистрация до оплаты.
- S11: Регистрация после оплаты (guest checkout -> account claim).
- S12: Invite-only регистрация (текущий рабочий сценарий).

### 2.4 Payment (симуляция Stripe)
- S13: Успешная оплата.
- S14: Отмена оплаты пользователем.
- S15: Ошибка карты/3DS.
- S16: Повторная попытка оплаты.
- S17: Webhook задержался, UI показывает pending.

### 2.5 Workspace / Company onboarding
- S18: Создание workspace.
- S19: Создание первой компании.
- S20: Пропуск необязательных настроек и быстрый старт.

### 2.6 Team flow
- S21: Solo-режим (1 пользователь).
- S22: Приглашение сотрудника.
- S23: Принятие приглашения сотрудником.
- S24: Назначение/смена роли.
- S25: Отключение/удаление сотрудника.

### 2.7 Основная CRM-работа
- S26: Создание лида/клиента.
- S27: Указание источника лида.
- S28: Движение по статусам.
- S29: Добавление заметок.
- S30: Постановка задач.
- S31: Работа с pipeline/dashboard.

### 2.8 Subscription management in-app
- S32: Просмотр текущего тарифа и лимитов.
- S33: Запрос дополнительных мест.
- S34: Видимость даты окончания лицензии.

### 2.9 Edge cases
- S35: Пользователь не завершил регистрацию.
- S36: Пользователь не оплатил.
- S37: Пользователь оплатил, но не вошел.
- S38: Пользователь оплатил и сразу отменил.
- S39: Удаление сотрудника/выход сотрудника из команды.
- S40: Удаление клиента/ошибки данных/пустые состояния.

## 3) Найденные проблемы (UX/логика/конверсия)

### Критичные (влияют на продажу CRM)
- P1 (Critical): Нет полноценного CRM landing + pricing funnel; публичный вход ориентирован на candidate intake, не на покупку CRM.
- P2 (Critical): Нет self-signup для нового CRM-клиента (только login/invite), из-за этого почти невозможен self-serve рост.
- P3 (Critical): Нет Stripe checkout/подписки в пользовательском потоке (billing сейчас как license/team-admin).
- P4 (Critical): Нет единого пути `Landing -> Trial/Payment -> Workspace activation`.

### Высокие
- P5 (High): `Settings/Billing` фактически редиректит на users/settings, а не на платежный кабинет клиента.
- P6 (High): Нет четкой модели тарифов Starter/Team/Pro в UI для конечного покупателя.
- P7 (High): Onboarding ограничен созданием компании; отсутствует guided first-value путь (клиент/лид/задача).
- P8 (High): Сильная зависимость от админ/суперадмин операций для лицензий и мест (не self-service).

### Средние
- P9 (Medium): Риск путаницы терминов (`tenant`, `workspace`, `company`, `client portal`) для нового пользователя.
- P10 (Medium): Недостаточно явных объяснений, какие шаги обязательны, а какие можно отложить.
- P11 (Medium): Отсутствует явный recovery-flow для случаев `оплатил, но webhook не обработан`.

## 4) Рекомендации (что упростить, убрать, добавить)

### 4.1 Что добавить в первую очередь (MVP конверсии)
1. Отдельный CRM landing (`/`) с value proposition, ICP, тарифами, FAQ и CTA `Start free trial`.
2. Self-signup (`/signup`) + email verification.
3. Stripe Checkout flow:
4. `select-plan` -> `checkout` -> `success`/`cancel`.
5. Webhook-обработка (`checkout.session.completed`, `invoice.paid`, `customer.subscription.updated/deleted`).
6. Customer Portal для смены тарифа/отмены/обновления карты.

### 4.2 Идеальный платежный flow (симуляция Stripe)
1. Пользователь выбирает тариф.
2. Создается `checkout_session` с `tenant_id`, `plan_code`, `trial_days`.
3. Редирект на Stripe Checkout.
4. При успехе Stripe отправляет webhook.
5. Бэкенд активирует подписку и лимиты tenant.
6. Пользователь возвращается на `/billing/success`.
7. UI показывает `Подписка активна`, запускает onboarding checklist.
8. При отмене -> `/billing/cancel` с CTA `Попробовать снова`.
9. При ошибке оплаты -> понятная причина + кнопка retry.

### 4.3 Что упростить в onboarding
1. После создания компании показывать 3 шага first-value:
2. Добавьте 1 клиента.
3. Добавьте 1 лид/кандидата.
4. Создайте 1 задачу или заметку.
5. Сделать явное разделение:
6. Обязательные поля для старта.
7. Продвинутые настройки позже.

### 4.4 Тарифы (рекомендуемая продуктовая рамка)
- Starter: 1 пользователь, базовый CRM, ограничение по активным лидам/клиентам.
- Team: несколько пользователей, роли/доступы, базовые автоматизации.
- Pro: расширенная аналитика, интеграции, продвинутые workflow.
- Для каждого тарифа: что включено, лимиты, что происходит при превышении, логика апгрейда.

### 4.5 Edge-case политика
1. Не завершил регистрацию: серия reminder + сохранение черновика.
2. Не оплатил: мягкий paywall + возврат к checkout без потери контекста.
3. Оплатил, но не вошел: welcome email + magic link.
4. Оплатил и сразу отменил: доступ до конца периода + win-back сценарий.
5. Удаление сотрудников/данных: подтверждения, audit log, recover window.

## Ключевой вывод

Текущая архитектура CRM внутри workspace функционально сильная (роли, модули, команда, onboarding компании, рабочие сущности), но коммерческий self-serve контур (`landing -> pricing -> signup -> payment -> activation`) сейчас фактически отсутствует.  
Главный блокер конверсии: нет прямого пути нового платящего клиента от первого касания до активной подписки.

## 5) Добавлено в план: реархитектура Settings по уровням ответственности

Цель: перестроить настройки вокруг ответственности пользователя, а не вокруг технической реализации backend.

### 5.1 Целевая модель уровней
- `Super Admin` (скрыто от клиентов): планы, лимиты, Stripe, feature flags, глобальная безопасность, аудит, API/platform.
- `Workspace / Organization`: профиль компании, брендирование, timezone/currency, CRM-базовые правила.
- `Team`: пользователи, роли, права, приглашения, распределение лидов, уведомления команды.
- `Personal`: профиль, язык, личные уведомления, пароль/безопасность.

### 5.2 Целевая IA интерфейса
- `Settings`
- `Workspace`
- `CRM Setup`
- `Team`
- `Automations`
- `Integrations`
- `Billing`
- `Personal`

### 5.3 Правила дизайна настроек
- Клиент не видит системные платформенные настройки.
- Новый пользователь должен начать работу без входа в `Settings`.
- До старта работы обязательны только критические настройки, остальные отложены.
- Верхний лимит: 6-7 разделов и 20-40 пользовательских настроек.

### 5.4 Рабочий план внедрения
1. `Инвентаризация`: собрать реестр всех текущих настроек (параметр, где используется, кто меняет, частота).
2. `Классификация`: пометить каждую настройку как `Core`, `Operational`, `Rare`, `Technical`.
3. `Уровни доступа`: назначить `Super Admin`, `Owner`, `Admin`, `User`.
4. `Удаление/скрытие`: убрать дубли, неэффективные и технические параметры из клиентского UI.
5. `Реорганизация IA`: перегруппировать текущие экраны в целевую структуру `Workspace/CRM Setup/Team/...`.
6. `UX-валидация`: проверить сценарий "зарегистрировался -> создал клиента -> начал работу" без посещения `Settings`.

### 5.5 Критерии готовности
- 100% системных настроек скрыты от tenant-пользователей.
- Не менее 30% текущих настроек удалены/скрыты/автоматизированы.
- Новый пользователь начинает операционную работу без обязательной конфигурации в `Settings`.
- Структура `Settings` соответствует ролевой модели, а не техническим подсистемам.

### 5.6 Визуальная стандартизация иконок (Tabler Icons)
- Принято решение использовать единый набор `@tabler/icons-react` по всей CRM.
- Базовое внедрение выполнено в ключевых зонах:
- глобальная навигация (`Sidebar`);
- top-level действия и уведомления (`Topbar`);
- карточки разделов настроек (`Settings Landing`).
- Следующий этап rollout:
1. Заменить локальные inline `svg` в рабочих модулях (Candidates, Companies, Documents, Communications).
2. Убрать emoji-иконки из конструкторов/редакторов и заменить на Tabler.
3. Ввести единый `icon map` по доменам (navigation/actions/statuses) и запретить ad-hoc svg в новых PR.
4. Провести UI-аудит на консистентность размеров (`16/18/20`) и stroke (`1.8/2.0`) иконок.

### 5.7 Статус реорганизации Settings (выполнено в текущей итерации)
- `Settings Landing` перегруппирован по ответственности:
- `Workspace`, `CRM Setup`, `Team`, `Automations`, `Integrations`, `Billing`, `Personal`.
- В карточках настроек добавлены недостающие домены:
- `Company access` (`/app/settings/company-access`) в `Team`;
- `My profile` (`/app/profile`) в `Personal`.
- Sidebar синхронизирован с фактическими экранами настроек:
- добавлены пункты `settings-billing`, `settings-legal`, `settings-company-access`, `settings-email`, `settings-tenant-links`;
- обновлен порядок admin-блока, чтобы отражать рабочую последовательность настройки CRM.
- Для новых пунктов добавлены Tabler-иконки и i18n-ключи (`en/ru/pl`), чтобы исключить fallback на технические key names.

## 6) Продолжение плана (Sales Launch Execution Order)

Цель: довести путь `Landing -> Signup -> Payment -> Active usage` до продаваемого состояния без ручных операций.

### 6.1 Сделано в этой итерации
- `Settings / Billing` больше не редиректит в users/settings; подключен отдельный billing-экран.
- Добавлен продуктовый экран управления подпиской с симуляцией Stripe-сценариев:
- выбор плана (`Starter/Team/Pro`);
- симуляция `success/cancel/error`;
- фиксация активного плана (временная локальная модель для UX-валидации);
- визуализация идеального Stripe flow в интерфейсе.
- В `Settings Landing` добавлен отдельный раздел `Billing`.
- В sidebar добавлена отдельная навигация и иконка для `settings-billing` (Tabler).
- Реализован backend `Billing API` на уровне tenant:
- `GET /api/v1/settings/billing/subscription`;
- `POST /api/v1/settings/billing/checkout-session`;
- `POST /api/v1/settings/billing/checkout-session/{session_id}/simulate`;
- `POST /api/v1/settings/billing/portal`;
- `POST /api/v1/settings/billing/webhook` (валидация подписи при подключенном Stripe, иначе безопасная заглушка).
- Billing UI переведен с локальной симуляции на реальные API вызовы.
- Добавлен явный `First Value` этап после создания компании:
- новый экран `/app/onboarding/getting-started` с 3-step запуском (клиент -> лид -> next action);
- обновлен redirect после создания компании: сразу в guided start;
- обновлен onboarding widget в Dashboard: чеклист ориентирован на операционную ценность, а не на техническую конфигурацию.
- Усилен `Public Pricing` как продающий этап:
- добавлены `best-for` подсказки по каждому тарифу;
- добавлена таблица сравнения планов;
- добавлен блок возражений (`common blockers`);
- добавлен FAQ;
- добавлен финальный CTA-блок на signup.
- Усилен `Signup-first flow` в точке входа `/login`:
- удален блок, уводивший новых CRM-пользователей в нецелевой public intake path;
- добавлен явный сценарий для новых клиентов: `Create account` / `View plans`;
- зафиксирован единый messaging: `Landing -> Signup -> Company -> First Value`.
- `Activation UX` переведен на data-driven статус:
- расширен `/api/v1/onboarding/status`: `activation_required`, counts (`companies/leads/reminders`) и step flags;
- `AppShell` теперь направляет admin/superadmin в `/app/onboarding/getting-started`, пока не выполнены шаги first value;
- `Getting Started` и dashboard onboarding widget показывают реальный прогресс по данным tenant, а не локальные отметки.
- `Subscription self-service` расширен:
- backend: добавлены `GET /api/v1/settings/billing/summary`, `POST /change-plan`, `POST /cancel`, `POST /reactivate`;
- backend summary теперь отдает связку `subscription + license + usage + available_plans`;
- frontend billing показывает статус/renewal/plan, прозрачные лимиты и использование, а также self-service действия без обращения в поддержку.

### 6.2 Следующие шаги (по порядку)
1. `Stripe integration (final step)`: подключить реальные `price_id`, Checkout и webhook events (`checkout.session.completed`, `invoice.paid`, `customer.subscription.updated`, `customer.subscription.deleted`) с записью статусов в tenant billing state.

### 6.3 Критерий завершения блока продаж
- Новый пользователь может пройти путь от landing до активной подписки без участия менеджера и без обращения в поддержку.
- Ошибки оплаты и отмена checkout не ломают сценарий и имеют понятный retry-flow.
- Биллинг прозрачен: текущий план, лимиты, дата продления и действия по подписке видны в 1 экране.
