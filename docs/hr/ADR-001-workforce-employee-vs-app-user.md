# ADR-001: Workforce Employee vs приложательный User и оргструктура

**Статус:** принято  
**Дата:** 2026-04-29  
**Контекст:** модуль HR (`docs/hr/module-scope.md`), экран «HR · Employees», админка пользователей и оргструктура.

## Контекст

В системе одновременно существуют:

1. **`users`** — учётные записи для входа в воркспейс: роли, ACL компаний, `supervisor_id` (линия отчётности в операционном CRM).
2. **`workforce_employees`** — кадровая запись о принятом человеке в HR-контуре: статус найма, даты, связь с кандидатом/`candidate_snapshot`, спутниковые HR-сущности (документы, профили и т.д.).
3. **`org_units` / `org_unit_members`** — формальная оргструктура и членство **пользователей тенанта** в узлах.

Пользователь ожидает ясной модели: кто «сотрудник в HR», кто «пользователь приложения», как это стыкуется с отделами.

## Решение

| Сущность | Назначение | SSOT |
|----------|------------|------|
| **User** | Аутентификация, RBAC, доступ к CRM/Fleet/HR по разрешениям; поле **supervisor** — операционный менеджер (рекрутинг и смежные сценарии), не оргдерево. | Таблица `users` + членства/роли. |
| **WorkforceEmployee** | Юридически/кадрово значимая запись о человеке как о нанятом сотруднике агентства; может существовать без логина (manual create); наследует контекст из кандидата при конверсии. | Таблица `workforce_employees`. |
| **OrgUnit / membership** | Формальные подразделения; членство задаётся для **User** тенанта (`org_unit_members`), не для `WorkforceEmployee`. | Таблицы `org_units`, `org_unit_members`. |

**Связь WorkforceEmployee ↔ User:** поле **`workforce_employees.linked_user_id`** (FK на `users`, `ON DELETE SET NULL`). Необязательно; не более **одного** HR-сотрудника на пользователя в пределах тенанта (проверка API). UI карточки HR подтягивает оргюниты через `org_unit_members` связанного пользователя.

**Оргструктура** остаётся привязанной к User: это отражает «кто из действующих аккаунтов в каком подразделении состоит» для доступа и отчётности по команде.

## Последствия

- HR Employees и оргструктура **не дублируют** друг друга: первый — жизненный цикл найма/HR-данных, вторая — дерево подразделений и членство аккаунтов.
- Поле **supervisor** у пользователя **не заменяется** оргструктурой; в UI даём пояснение рядом с обоими понятиями.
- Любое объединение каталога сотрудников с оргюнитами через одну сущность потребует отдельного ADR и миграции данных.
