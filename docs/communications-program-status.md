# Communications Program Status (Omnichannel + Email + Calendar + Planner)

## Цель (исходная задача)
Сделать полноценный модуль коммуникаций для CRM:
- сообщения из разных мессенджеров;
- входящие/исходящие email;
- распределение по менеджерам (очередь, графики, занятость);
- календарь и планировщик задач;
- управление доступом и подпиской (tenant-level и role/user-level внутри tenant).

Важно:
- `Messages`, `Email`, `Calendar`, `Planner` разделены по UX (не в одном месте).
- настройки вынесены в `Settings -> Communications`.
- поддержка тестирования работы каждого менеджера/очередей/графиков/тайм-офф/каналов.

## Что уже реализовано (по состоянию на сейчас)

### 1. Omnichannel communications core (backend)
- `communication_threads`
- `communication_messages`
- `communication_channel_accounts`
- API `/api/v1/communications/*` (threads/messages/accounts/ingest/dispatch)
- Telegram MVP (inbound simulate + public webhook + outbound via Bot API)
- Email MVP:
  - inbound ingest endpoint
  - IMAP adapter MVP
  - SMTP dispatch через tenant SMTP

### 2. Manager queue / schedules / availability
- tenant settings `/api/v1/settings/communications`
- queue strategies:
  - `manual`
  - `round_robin`
  - `weighted_round_robin`
  - `least_busy`
- учитываются:
  - графики
  - availability state
  - capacity/load
- allocator preview (dry-run)
- allocator audit log (DB + API + UI)

### 3. Time-off requests + approvals
- `communication_time_off_requests`
- employee flow (`/app/my-availability`)
- manager approval flow (`/app/time-off`)
- approved time-off влияет на allocator
- approved time-off синхронизирует queue availability (`offline`)
- `partial_day` поддерживает точные интервалы через `payload.time_window`

### 4. Scheduler (backend loop)
- lifecycle startup/shutdown в `FastAPI`
- периодические:
  - email poll worker
  - email dispatch worker
  - SLA escalations по communication threads
- runtime status + manual run:
  - `GET /api/v1/communications/scheduler/status`
  - `POST /api/v1/communications/scheduler/run-now`
- UI панель scheduler в `/app/settings/communications`

### 5. SLA policy + escalations
- `sla_due_at` вычисляется автоматически по channel policy (`responseSlaMinutes`)
  - на inbound message
  - сбрасывается на outbound reply
- scheduler создает:
  - in-app notification
  - reminder
  для просроченных неотвеченных тредов (идемпотентно через `thread_meta`)

### 6. Calendar (новый `/app/calendar`)
Unified calendar:
- `time-off`
- `reminders`
- `communication SLA`
- `planner events`

Фильтры:
- source (`all/timeoff/reminders/communications/planner`)
- time-off status (`approved/pending/all`)

### 7. Planner (новый `/app/planner`)
`communication_planner_events`:
- список
- создание события
- фильтры (`status`, `kind`)
- быстрые смены статуса (`planned/in_progress/done/cancelled`)
- planner events отображаются в `/app/calendar`

## Важные технические решения
- Основной путь для схемы: **Alembic migrations**
- `ensure_communications_schema()` оставлен как fallback для SQLite/dev bootstrap
- Tenant-level communications settings хранятся в `Tenant.settings["communications"]`
- Secrets (Telegram token / IMAP password) шифруются на backend

## Недавние проблемы и фиксы (чтобы не потерять)
- Postgres `UndefinedTableError: communication_threads`
  - причина: bootstrap был только для SQLite
  - фикс: Alembic migrations + non-sqlite fallback create_all
- Frontend `422` + React error #31 на `/calendar` и `/team-availability`
  - причина: `limit > 200` (FastAPI validation)
  - фикс: лимиты <= 200 + безопасный рендер ошибок (`detail` array/object)
- Unread/notifications drift (SLA и сообщения)
  - причина: исторический шум SLA + рассинхрон `thread.unread_count` vs фактические unread inbound messages
  - фикс:
    - `POST /api/v1/communications/threads/reconcile-unread` (пересчет unread по факту `read_at is null`)
    - `POST /api/v1/notifications/reconcile` (user-level cleanup stale SLA notifications)
    - `POST /api/v1/notifications/reconcile-tenant` (tenant-wide cleanup, supervisor/admin/superadmin)
    - Telegram command inbound (`/start`, `/bind`, etc.) больше не увеличивает unread
    - SLA alerts auto-resolve при outbound reply и при `no_reply_needed`
  - one-time data cleanup выполнен:
    - tenant `11111111-1111-1111-1111-111111111111`
    - users processed: `2`
    - stale notifications marked read: `24`

    - `backend/app/services/communications_oauth.py`

    - timeout/error mapping с явными HTTP деталями
  - backend inbox poll adapter добавлен:

    - Gmail (`gmail/v1/users/me/messages`) poll + message hydration

## Как продолжать работу (рабочий порядок)
1. Делать изменения по доменам (`messages/email/calendar/planner/availability`) без смешивания UX.
2. Любую новую persistence-сущность добавлять через Alembic.
3. После backend-изменений:
   - `py_compile`
   - `docker compose exec backend ... alembic upgrade heads` (если есть migration)
   - restart backend
4. После frontend-изменений:
   - `npm --prefix /opt/HostFlow/hostflow-frontend run build`
5. Legacy-функциональность переносить сразу в целевой модуль (`/app/messages`, `/app/email`, `/app/settings/communications`) без новых legacy CTA.
