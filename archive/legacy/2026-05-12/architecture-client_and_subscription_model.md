# Модель клиентов и подписок HostFlow

## Назначение

Зафиксировать различие между клиентом **с тенантом** (партнёр, полный доступ) и клиентом **без подписки на HostFlow** (ограниченный доступ). Функциональность должна разграничиваться по типу подписки; возможность для этого заложена в модели и лицензиях.

---

## 1. Два типа клиентов

| Тип | Описание | Тенант | Подписка | Доступ |
|-----|----------|--------|----------|--------|
| **Клиент с тенантом (партнёр)** | Клиент со своей учётной записью HostFlow, отдельный tenant. | Есть (`Tenant.type = company`). | Есть (полная или по плану). | Полный доступ в рамках своего тенанта: кандидаты по своим вакансиям, handoff, документы, портал. |
| **Клиент без подписки на HostFlow** | Клиент без отдельного тенанта, доступ только через агентство (company под агентством). | Нет отдельного тенанта. | Нет подписки на HostFlow. | Ограниченный доступ: только то, что агентство открыло (портал компании, handoff в компанию и т.д.). Функции ограничиваются по типу/наличию подписки. |

---

## 2. Текущая реализация и задел

- **Тип тенанта:** `Tenant.type` (`TenantType`: `agency` | `company` | `platform`) — позволяет отличать агентство от клиентского тенанта (company).
- **Лицензия:** `TenantLicense` (план `plan`, лимиты `max_*`, `expires_at`) — привязка подписки к тенанту. Логика ограничений по плану реализуется в сервисном слое.
- **Определение «клиентский тенант»:** в коде используется `is_client_tenant(db, tenant_id)` — тенант с `type == company`. Такой тенант считается клиентом с собственным входом и (при наличии лицензии) полным доступом.

**Партнёр Citronex (Citronex Trans Logistic):** клиент с собственным тенантом и своей подпиской; для агентства выступает как «клиент» (получает handoff, видит кандидатов по своим вакансиям). Должен видеть **всю свою базу кандидатов** (свои + от агентства по вакансиям клиента). Кандидатов, которых агентство **не передало** (нет handoff в тенант клиента), клиент видит только в **урезанном виде**: в списке и в карточке без PII (имя, email, телефон скрыты; отображаются «Кандидат #short_id» и short_id). Переданные (handoff в тенант) и свои (candidate.tenant_id == тенант клиента) отображаются с полными данными. Тестирование ведётся на полной версии подписки.

**Требование к `tenant_links` для полного списка кандидатов у клиента с тенантом:** в `tenant_links` должна быть хотя бы одна строка с `client_tenant_id = <UUID тенанта клиента>` и `handoff_include_company_id = <UUID компании>`, чьи вакансии считаются вакансиями клиента. Без такой связи в scope и RLS попадают только кандидаты с handoff или из своего тенанта; маска PII для непереданных кандидатов также зависит от распознавания клиента (через `client_tenant_id` или тип тенанта `company`).

**Почему видно только N кандидатов:** в выборку попадают только кандидаты по вакансиям **тех компаний**, для которых есть строка в `tenant_links` с данным `client_tenant_id` и `handoff_include_company_id = <id компании>`. Если у агентства несколько компаний с вакансиями, а в связях указана только одна компания — клиент видит только кандидатов по вакансиям этой компании. Чтобы клиент видел всех кандидатов по «своим» вакансиям, нужна отдельная строка в `tenant_links` на каждую такую компанию (один и тот же `client_tenant_id`, один `agency_tenant_id`, разный `handoff_include_company_id`). Миграция `202602080007` для Citronex добавляет такие связи по всем компаниям агентства, у которых есть вакансии.

## 3. Разграничение функций по подписке

- Ограничения по подписке должны применяться по данным **тенанта** и **лицензии** (`TenantLicense.plan`, лимиты, `expires_at`).
- Для клиента **без тенанта** (доступ только как company под агентством) функции ограничиваются явно: только то, что предусмотрено для «клиента без подписки».
- Для клиента **с тенантом** набор возможностей задаётся планом лицензии (например, полный доступ для партнёров, ограниченный — для других планов).

Реализация проверок: в сервисном слое и API при необходимости вызывать проверку лицензии/плана тенанта и ограничивать доступ к фичам или объёму данных. Конкретные правила по планам (какие функции доступны на каком плане) задаются в коде и при необходимости в конфигурации.

## 4. Диагностика (клиентский список кандидатов)

В ответе GET списка кандидатов при запросе от клиента бэкенд добавляет заголовки:
- `X-Client-View: 1` — запрос обработан как клиентский (scope и маска PII включены).
- `X-Masked-Count: N` — число элементов с `masked === true` (урезанная карточка без PII).

По ним в браузере (Network → запрос к `/api/v1/candidates` → Response Headers) можно проверить: отсутствие `X-Client-View` означает, что тенант не распознан как клиент; при `X-Masked-Count: 0` маска не применилась (все считаются переданными/своими или ошибка в данных/связях).

## 5. Scope и доступ по типу тенанта и порталу

### 5.1 Тенант типа agency (агентство)

- Видит своих кандидатов (candidate.tenant_id = agency) и кандидатов по привязанным клиентам (tenant_links).
- В разделе «Клиенты» управляет связями (tenant_links): создание клиента по имени, привязка к существующей компании (поиск по имени/домену в тенантах с `Tenant.type = company`), настройки handoff_enabled, see_vacancies, see_reduced_profiles.
- Для клиента без тенанта может выдать **ссылку портала** (portal_token в tenant_links): POST `/tenants/{id}/links/{link_id}/portal-link` создаёт/обновляет токен; DELETE отзывает. Клиент без входа открывает `/client-portal?token=...` и видит только переданных (accepted handoff) кандидатов в режиме только чтения; при see_reduced_profiles PII маскируется.

### 5.2 Тенант типа company (прямой работодатель / клиент с тенантом)

- Видит своих кандидатов и кандидатов по вакансиям компаний, указанных в tenant_links (handoff_include_company_id при client_tenant_id, или client_company_id). Маска PII для непереданных кандидатов (см. раздел 2).
- Не создаёт tenant_links; связь создаётся со стороны агентства.

### 5.3 Доступ по ссылке портала (без тенанта)

- Запрос `GET /api/v1/public/client-portal?token=...` не требует авторизации. По токену определяется tenant_link; возвращаются company_name и список кандидатов с accepted handoff в этого клиента (по client_company_id или client_tenant_id + handoff_include_company_id). Режим только чтение; при see_reduced_profiles поля email/phone и др. не возвращаются.
- Поля tenant_links: `portal_token`, `portal_expires_at` (опциональный срок действия).

## 6. Связанные артефакты

- Модели: `backend.app.models.tenant` (`Tenant`, `TenantType`, `TenantLicense`, `TenantLink` с полями portal_token, portal_expires_at).
- Определение клиентского тенанта: `backend.app.services.handoff.is_client_tenant`, `is_client_tenant_for_list` (для списка и маски PII).
- Список кандидатов и маска: `backend.app.api.v1.candidates.router` (`list_candidates`, `_apply_client_view_mask`), `backend.app.api.v1.candidates.repo` (`_candidate_scope_clause`).
- Портал клиента по ссылке: `backend.app.api.public.client_portal` (GET по token), `backend.app.api.v1.tenants.router` (POST/DELETE portal-link).
- Архитектура мультитенантности: `docs/specs/architecture/multi_tenant_model.md`.
